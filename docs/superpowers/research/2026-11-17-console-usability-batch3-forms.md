## 2. What `ui/forms.js` already supports (410 lines)

- `simpleForm({fields, submitLabel, onSubmit, draftKey, timeZone, ctx})` (l.331). Field spec: `{name, label, type, value, required, step, options, suggestions}`. `control()` (l.~158): types `textarea`, `select` (options = values or `{value,label}`), `number` (attr `step`, default "any"), `datetime` (datetime-local, converted to epoch seconds via `zonedToEpoch` in the operator's zone, zone label shown), `password`, `hidden`, anything else -> text. Not supported: min/max/maxlength/pattern attributes, checkbox/radio/multi-select, help/hint text beside a field, unit suffix, per-field `rows`/monospace, repeating rows, grouped sub-forms, custom (non-flat) request body, dynamic dependent fields.
- Validation: `convert()` (l.~203): empty required -> `form.required`; number via `Number()` (`form.badNumber`); datetime (`form.badTime`); empty optional fields are OMITTED from the values (so server defaults apply). No client min/max check - only server 422.
- Server 422 -> `handleFailure` (l.~125) -> `placeFieldErrors(entries, fieldErrors, ctx)` (l.~236): matches each error's `loc` path parts against field NAMES, shows message beside the field; non-matching go to the status line as located text (`locatedText`: the ugly `protocol › treatments › 0 › id`, ERR-02); hidden-field errors become lines labelled with the field label. So flat field names equal to server leaf names (`question`, `max_calls`, `script`) get inline errors for free; nested names (`analysis.method`) need `name` = last loc part (e.g. `method`, `primary_endpoint`) - uniqueness of leaf names matters (a name found anywhere in `loc` wins).
- Drafts: `draftKey` -> `takeDraft`/`saveDraft` (W/drafts.js); `keepOnSessionLoss` saves raw values (never passwords) on a 401/"session" error and when page leaves; `registerDraftSaver`; restored draft shows `form.draftRestored`. `editFold` (project-forms.js:12) opens the fold when `hasDraft(draftKey)`.
- Test hook: `formControls(form)` -> `{get,set,suggest,focus}` (l.313); `suggestions` produce a `<datalist>` refillable via `suggest(name, values)` (used in stage-measurements.js:83).
- `jsonEditor` (l.372): single textarea `json`, class `input-code`, rows 8..30, parse error `form.badJson`, 422 via `placeFieldErrors([], ...)` (so every error is a status line), draft `{text}`. This is the thing to demote to the "advanced" fold.
- Reusable bits outside forms.js: `confirmAction(t,{title,lines,confirmLabel})` (W/ui/dialog.js); `techDetails`/`note`/`section`/`afterWrite` (W/ui/section.js); `details.edit-fold` styling; `formatDuration`, `levelText`, `DEFAULT_LEVEL_RANGES`, `unitText` (W/format.js, pages/safety-text.js).
- Needed new building blocks (propose a new file W/ui/field-forms.js or extend forms.js, keep <800 lines; forms.js is 410): (a) field attrs `min`,`max`,`maxlength`,`hint`,`unit`; (b) `fieldset`/section grouping; (c) a repeatable-row group (add/remove row) for treatments, rules, lists; (d) a `lines` list field (textarea -> array); (e) `advancedJson(form, value)` wrapper: a `<details>` containing a `jsonEditor` that overwrites/loads the form values. Mixed bodies (nested object from flat fields) need a `build(values)` step; simpleForm's `onSubmit(values)` can already do that (callers shape the body, e.g. startRoundForm).

## 7. Hard parts and proposed form scope

- Safety (cleanest to form-ify): rules[] as repeatable rows: id (text; default suggest `<sensor>-<channel>-<n>`), sensor (select from `SENSORS` keys, labelled with `metric.*`, unit shown as suffix and written into `unit`), op (select, labels via `safety.op`), trigger value (number + unit suffix), duration (number of seconds shown with exactText hint), validity (seconds), action channel (select light/exhaust/fan; pump level only 0..1), level (number with min/max from level_ranges, range text beside it). Frozen: one number row per sensor in SENSORS (blank = not checked), minutes 0 < x <= 1440, max gap seconds 0 < x <= 3600. Whole object -> same `approver` -> same diff dialog. Advanced fold: the current jsonEditor with the full config, both ways in sync (on form submit use the form values; the fold submits its own JSON). Prefill: `state.current`; if null -> zero rows + an "add rule" button + empty required frozen fields + range hint beside each (decision 7). Server-side bounds to mirror client-side: frozen minutes (0,1440], gap (0,3600], levels per range. validity/duration have none server-side (still require >= 0 client-side; ProtectionRule gives no bound) - state that in the plan so the form doesn't invent limits.
- Protocol (hardest): treatments[] (id, name, factors = key->number|text pairs) and allocations[] (round, block, unit, treatment_id) are variable-length nested lists, `rounds * blocks` allocations typically. Proposal: form covers scalars + treatments rows (id, name, description, one-to-few factor pairs) + analysis (primary endpoint, target effect, method, exclusions as lines, the two fraction caps, defaults 0.2/0.1) + crop, batch, experimental_unit, seed, stages (comma list), rounds, blocks, `control_treatment_id` as a select of the treatment rows; ALLOCATIONS stay in the advanced JSON fold by default but are GENERATED when the operator leaves them blank? NO - do not silently invent a randomisation: either (a) a simple allocation table (rows = round x block x unit, treatment select), or (b) require the fold. Recommend (a) as a repeatable row group only if time allows; otherwise protocol form ships with allocations in "advanced" and the plan says so explicitly. id/project_id/version: hidden/derived (project id from page; version = latest saved version for that protocol id + 1 or 1 - the `protocolExample` id scheme `protocol-<n>-<last6>` is kept as the default id). `question` required (client-side), `hypothesis` required only by habit (model allows empty) - match inventory: question required.
