# 控制台可用性改造：设计

状态：2026-11-16 由助手起草，待用户审阅。用户的决定：按三批改（"按三批来"）。
清单：[`2026-11-16-console-usability-inventory.md`](2026-11-16-console-usability-inventory.md)（116 条问题，10 个根源 C1–C10，编号 E-/R-/S-）。

## 为什么

用户看了 11 月 15 日实跑的截图后说："问题不是中文还是英文，而是直接显示内部字段比较扎眼，对用户不好。"随后要求"根据这几个标准进行全方面改造"。这几个标准是：

- 尼尔森十大可用性原则（N1–N10），尤其是 N2（用用户熟悉的说法，不用系统内部术语）、N8（简约，不让无关信息抢注意力）、N9（错误要说清发生了什么、怎么办）；
- ISO 9241-110 交互原则：任务适合性、自我描述性、符合用户预期、容错；
- 渐进式呈现：大多数人需要的先显示，技术细节折叠；
- 代码与文案分离：程序内部传代码，界面经对照表显示说法。

清单显示，问题集中在 10 个根源上，大多数根源用一个全站共用的机制就能修好，而不是逐页修。

## 目标

1. **界面上不出现内部字段。** 事件码、枚举值、字段名、自动生成的 id、哈希、原始时间戳、payload 字典，只能出现在"技术详情"里。
2. **每条错误、告警、检查结果都能读懂：** 一句发生了什么，一句下一步做什么。
3. **数字、时间、时长用人的单位：** 21 天而不是 504.0 小时，"风扇 3 / 10"，按界面语言显示日期时间。
4. **有后果的操作先拦一下，并说明后果；高风险设置用分字段的表单，不用整份 JSON。**
5. **模型写给操作员的文字也遵守同样的规则。**
6. **防止复发：** 测试能发现新出现的"界面露出内部字段"和"代码没有对应文案"。

## 非目标

- 不改视觉风格和版式体系（颜色、字体、整体布局），只改内容、顺序和折叠。
- 不引入前端框架或构建步骤：控制台仍是原生 ES 模块，没有外部依赖。
- 不改业务规则：安全、审批、工作流状态和权限一律不变。
- 不删任何可追溯信息：id、摘要、原始事件都保留在"技术详情"和 API 里。

## 反目标（即使能用也算失败）

- 技术详情藏得太深：做审计或追溯时，必须一次点击就能看到并复制。
- 文案和代码重新耦合：新增一个代码却没有文案，测试必须失败。
- 中英文目录不同步：一边有的条目另一边没有。
- API 不兼容：旧客户端或日志依赖的 `message` 字段消失。

## 约束

- 控制台：`src/growbridge/web/workbench/`，文案在 `i18n/en.js`、`i18n/zh.js`；测试是 `node --test tests/web/*.test.mjs`，不用浏览器、服务器和网络。
- 服务器：Python 包 `growbridge`；`pytest`、`ruff`；文件不超过 800 行，函数少于 50 行；TDD。
- 已有可复用的东西：`statePill`/`severityPill`（`ui/status.js`）、`confirmAction`/`confirmedButton`（`ui/dialog.js`、`ui/section.js`）、`questionCell`（`pages/project.js`，长文本截断展开）、`formatTime`/`formatNumber`（`format.js`）、`describeDenial`（`denials.js`，33 个拒绝码都已有文案）、`research/notes.py`（代码 + 中英文文案的模式）。

## 方案

| | 方案 | 取舍 | 结论 |
| --- | --- | --- | --- |
| A | 一次全改 | 一次见效，但改动巨大，一个 PR 无法认真审，也容易和其他分支冲突 | 不采用 |
| B | 按根源分三批，每批一个 PR | 共用机制先做，后面每页的改动都很小；每批可单独审；第一批只动控制台，风险最低 | **用户选定** |
| C | 按页面逐页改 | 显示名、格式这类共用机制会在各页重复做，而且做得不一致 | 不采用 |

## 共用规则（三批都遵守）

- **G1 名字：** 用户看到的是名字或序号（"项目：生菜光照系列"、"第 1 轮"、"第 1 阶段 · 营养生长"），不是 id。id 只出现在技术详情里，可复制。
- **G2 代码经目录：** 任何代码都通过对照表变成文字；对照表里没有的，显示"未知（技术详情）"，绝不直接显示代码。
- **G3 技术详情：** 全站一个折叠组件；默认收起，展开后显示完整 id、哈希、原始事件，每项可复制。界面正文里需要指代哈希时，只显示短指纹（前 8 位加 "…"）。
- **G4 数字和时间：** 时长按大小用天、小时、分钟、秒；档位写成"值 / 满档"；日期时间按界面语言格式化，时区只在页头写一次；钱按语言格式化，不出现浮点误差。
- **G5 消息格式：** 错误、告警、检查结果、拒绝原因都是"发生了什么"加"下一步做什么"两句；内部异常只显示固定的人话，异常类名进日志。
- **G6 有后果的操作：** 先确认，确认框里一句话说明后果；选择框默认是"请选择…"；输入框限制范围。

## 第一批：只改控制台（C1、C2、C3、C6、C10）

**新的共用件**
- `ui/names.js`：`displayName(t, kind, row)`，kind 包括项目、轮次、阶段、快照、任务、计算尝试；规则按 G1。读接口缺序号或名字的地方，服务器读接口补字段（如轮次的协议轮次号、阶段在轮次里的序号和生长期名）——这是第一批里唯一允许的服务器改动，只加字段不改行为。
- `i18n.js`：`labelOr(t, prefix, value)`，按 G2 查表。覆盖：阶段事件、事件详情键、干预类型、检查结果码、告警类型、角色、状态、计算阶段、工具名、字段名。
- `ui/section.js`：`techDetails(t, entries)`，按 G3。
- `format.js`：`formatDuration`、`levelText`、`formatTime`（时区不再每格重复）、`formatMoney`，按 G4。

**逐页应用**
- 阶段历史：每条事件变成一句话（"到达计划时长，阶段结束"），详情里的已知键变成标注过的短句，未知键和原始值进技术详情；新的在上。
- 运行单：检查结果显示文字而不是 `manual_task` 这类码；摘要用短指纹；时长用天。
- 报告：标签"报告摘要"改成"报告指纹"（它是哈希，不是摘要）；快照 id、摘要进技术详情。
- 页面顺序和信息量按清单 C10 调整（例如审批按钮放到运行单后面；长文本截断加"展开"；"还有 N 项未显示"可以点开）。
- 覆盖的清单条目：C1、C2、C3、C6、C10 下列出的全部编号，以及零散项中属于显示的部分（由计划逐条分配）。

## 第二批：服务器发"代码加参数"（C4、C7）

- **消息结构：** 告警、运行单检查结果、拒绝原因、写入回执、阶段事件详情，都带 `code` 和 `params`（传感器、数值、单位、秒数、状态等），同时保留英文的 `message` 供日志和旧客户端使用。
- **拒绝码拆细：** 使用最多的 `state`（约 98 处）、`scope`（约 29 处）和 `approval_invalid` 拆成子码（如 `stage_not_pausable`、`run_sheet_too_old`、`capabilities_changed`），每个子码有自己的说明和下一步。
- **控制台目录：** `alert.<code>`、`finding.<code>`、`denial.<code>`、`event.<code>`，每条都有正文和 `.action`（下一步做什么），中英文各一份，用 `params` 填空。
- **防复发测试：** 服务器端列出它能发出的全部代码；控制台测试确认每个代码在两份目录里都有正文和下一步。
- 告警消息的英文旧文字继续写进 `message`，所以通知渠道（邮件、Telegram）在本批里不变。

## 第三批：表单、确认和模型（C8、C9、C5）

- **表单代替 JSON：** 安全上限、研究协议、保留集登记、冻结分析脚本、提交修改后的运行单，都改成分字段的表单（带单位、范围，指标和方法从协议里选）；整份 JSON 放进"高级"。目标的 JSON 编辑器删除（项目对话已经能提目标）。安全上限第一次进入时给一份已审定的模板，而不是全是 `null` 的骨架。
- **有后果的操作：** 清单 C9 列出的每个操作都用 `confirmAction`，确认框写明后果；轮次选择框默认"请选择…"；未审批时"启动"不可点；浇水表单和任务行里的浇水按钮一样先确认。
- **模型写作规则：** 在 `agents/roles.py` 的 `_COMMON_LIMITS` 里加一段共用规则：不写 id、字段名、工具名、枚举值；日期时间写本地时间，时长写分钟或天；每个问题一句话说明该做什么；控制长度；用操作员的界面语言。把界面语言随目标一起传给模型；监察任务的问题里不再出现 epoch 秒。

## 验收

- 每批结束时，清单里分配给这一批的条目全部关闭，每条要么有测试，要么有截图对照。
- **防露出测试（第一批建立，后两批沿用）：** 用页面测试夹具渲染每个页面，断言技术详情之外不出现这些形态：`snake_case` 代码、32 位以上十六进制 id、64 位哈希、10 位 epoch 秒、`{` 开头的 payload。
- **目录完整性测试：** 第一批覆盖控制台已知的代码集合，第二批扩展到服务器能发出的全部代码。
- 每批完成后，用开发工作台截取关键页面的中英文截图，与改造前对照。

## 实现前已定的事项（助手的决定，用户可改）

建造者审读后提出的问题，按下列方式定下：

1. **防露出测试怎么渲染页面：** 在 `tests/web/` 写一个最小的假 DOM（`ui/dom.js` 的 `h()` 只用到 `createElement`、`createTextNode`、`createElementNS`、`append`），各页用测试数据渲染后检查文字。测试数据取自 2026-11-15 实跑导出的真实接口返回（轮次、阶段、历史、人工任务、报告、对话、环境；模拟设备，不含密钥），存成 `tests/web/fixtures/*.json`。第一批覆盖它改到的页面，后两批随改随加。
2. **第一批时服务器还在发英文句子：** 告警消息、拒绝原因里的原始 `message`、运行单检查结果的说明、回执，这些"服务器整句"在第一批里照常显示，在防露出测试里列为明确的豁免清单（每项注明"第二批处理"）；第二批完成时清单必须清空。已经带代码的（检查结果码、告警类型、事件名，即清单 S-12、S-13、S-27–S-29），第一批就在控制台映射，不需要动服务器。
3. **清单的口径：** 以清单第 3 节逐页表格里合并后的 116 行为准，每行的编号格是它的正式编号；第 2 节的根源条数按原始 134 条计，只用于归类。中、低级别条目在实现时先确认还能复现，复现不了就记一笔关闭，不硬改。
4. **第一批的服务器读字段：** 只给页面真正要用的读接口加字段（轮次序号、阶段序号和生长期名），只加不改；照常 TDD、`pytest`、`ruff`，800 行、50 行的上限不变。字段缺失（旧数据）时显示"未命名轮次"这类通用说法，id 放技术详情。
5. **第二批的拒绝码：** 保留原来的粗码 `code`，新增 `reason` 放细分子码，加上 `params`，所以旧客户端不受影响；细分要覆盖全部抛出点，不是只举几个例子。服务器建一个集中的代码登记表，所有发出点都从它取码，这样"代码都有文案"的测试可以自动生成清单。邮件和 Telegram 通知在这次改造里保持英文 `message`，本地化通知不在范围内。
6. **界面语言怎么传给模型（第三批）：** 每次提目标时，请求带上控制台当前的语言，存进这个目标任务；规划、研究等后续任务继承它；监察这类后台任务用该项目最近一次目标的语言；都没有时用中文（与 `research/notes.py` 的 `TEXT_LANGUAGE` 一致）。
7. **安全上限的初始值（第三批）：** 绝不发明安全数值。表单从最近一次已批准的上限预填；从未批准过时，给空的必填项，每项旁边提示设备能力允许的范围，并保留审批对话框这道关。指标和方法的下拉选项来自已保存的研究协议。
8. **其他：**
   - 时区：用服务器配置的 `report_timezone`（控制台通过 `ctx.me.timezone` 已经拿到），页头写一次。
   - 相对时间（"5 分钟前"）：只用于 24 小时内的列表时间，详情页仍显示完整日期时间。
   - 改造前后截图：用开发工作台加脚本化的模拟轮次截取，不调用模型。
   - 技术详情：每项可复制，另加"复制全部"。
   - 删除目标的 JSON 编辑器前，先查清 `pages/project.js`、`pages/project-forms.js` 和 i18n 里的引用。
   - PR 的目标分支：如果前面的 PR 还没合进 `main`，就叠在它们最上面的分支上开 PR，和 #6 一样。
