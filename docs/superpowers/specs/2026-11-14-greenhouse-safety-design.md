# 三项安全补强：设计

**日期：** 2026-11-14 · **状态：** 已批准（2026-11-14） · **分支：** `feat/greenhouse-safety`

思路来自 [xdianlei/agentic-greenhouse](https://github.com/xdianlei/agentic-greenhouse)（`stuckwatch.py`、`prioritylock.py`、`supervisor.py` 的 `unexpected_pump`）。只借思路，不复制代码。

## 1. 意图

DiAGRI 的安全层有三个缺口，都在确定性代码里补，不经过模型：

1. **意外开泵没人管。** 规则保证 DiAGRI 自己不会自动开泵，但 AC5 面板和厂商 App 可以。外部改动检测只比较执行 Agent 自己写过的通道（`executor/engine.py` `_external_change`），所以泵被别处打开后，没有任何代码报警或关泵。泵一直开着是这套系统最大的物理风险。
2. **卡住的读数能骗过所有检查。** 规则用的读数只要求有值、质量 ok、单位对、够新（`executor/rules.py` `valid_reading`）。一个卡在 24.0 °C 的温度探头全部满足，于是过热保护永远不会触发，这段数据还会当作正常数据进入分析。
3. **保护写入要排队。** 控制服务的闸门是先来先服务的锁。操作员排了几条写入时，一条保护写入要等它们全部做完。核对代码时还发现：灌溉结束时的关泵（`control/service.py` `_run_cycle` 的 `finally`）也在同一个队列里排，所以泵可能比设定时长开得更久。

用户的决定：

- 实验期间没有人会从 AC5 面板或厂商 App 手动开泵（用户选择："No, never by hand"）。所以看门狗**默认直接关泵**，不只是告警。
- 水泵永远不交给 AC5 自己的定时器（用户选择："Never allowed"）。运行单校验要新增一条阻断来保证这一点，见 4.1。
- 读数冻结时，只有当前运行单或安全配置里有规则用到这个传感器，才暂停阶段（用户选择："Pause if a rule uses it"）。没有规则用到时只告警。
- 闸门分两级优先，见第 6 节（用户确认："Yes, write the doc"）。

## 2. 目标、非目标、反目标

**目标**

- G1 意外开泵：DiAGRI 模式下，读回显示水泵开着、而 DiAGRI 没有在灌溉，就经已有的 `pump_off()` 专用通道关泵，发 critical 告警，在动作账本和实验记录（干预记录）里留下记录。
- G2 冻结读数：按存储的样本，发现某个传感器的值长时间完全不变，就发告警，并写一条冻结时段标记。如果有规则用到这个传感器，暂停当前阶段。
- G3 闸门优先：保护写入、灌溉结束时的关泵、交接，最多只等正在执行的那一条写入。

**非目标**

- 不改 `pump_off()` 不进闸门这一点。
- 不打断正在执行的写入（不抢占）。
- 不改 `valid_reading`：冻结读数在规则里的判断不变，靠暂停和告警处理。
- 仅桥接模式不加看门狗，也不加冻结检测（那时没有执行 Agent 和观察者）。
- 不改工作台读数曲线里"已标记"样本的计数。
- 不引进对方仓库的其他功能（按次数的人工预算、方案里的定时浇水等）。

**反目标**（做成这样就算失败，哪怕功能能跑）

- 出现任何会让水泵自动打开的路径。
- 绕过账本或授权检查直接写设备（对方的看门狗直接调 `bridge.operate`，就是这种做法）。
- 修改或删除任何原始样本。
- 慢变化的传感器反复把实验误停下来。
- 让模型参与这三项判断。

## 3. 约束（来自现有代码）

- **闸门**：`control/service.py:69` `self.gate = asyncio.Lock()`。持有它的地方：
  - `handover()` `:162`：先吊销写权、作废排队的写入，再进闸门等正在执行的那一条；
  - `submit()` `:320`：所有普通写入，包括保护写入（保护写权先调 `_end_cycle()`，`:317`）、反馈和照料写入、操作员手动写入；
  - `_run_cycle()` `:441` 开泵、`:456` 关泵；
  - `reconcile_unsettled()` `:524`。
- **进闸门后先复查**：`_recheck`（`:397`）在 `submit` 和灌溉开泵里都是进闸门后的第一件事。被拒时记 VOID 并抛出。这个顺序不能变。
- **专用关泵通道**：`pump_off()`（`:479`）不进闸门。它调 `_end_cycle()`，用系统写权 0、触发名 `interlock` 记账，并用 `supersedes` 指向最后一条未结的水泵动作；没有未结水泵动作时也能用（`supersedes` 为 `None`）。关泵没确认时会设联锁。
- **执行 Agent 的 tick**（`executor/engine.py:142-164`）：第 1 步联锁、第 2 步保护在没有阶段时也运行；之后没有阶段就返回。
- **观察者**从不写设备，只拿到最新读数（`control_readings`）。`_pause`（`observer/service.py:51`）报 `ALERT_PAUSE`，事件编号来自告警的 `event_id`，所以一次告警事件最多暂停一次。
- **会让阶段暂停的事件**：`workflow/service.py:56` `PAUSE_KINDS`，含 `READINGS_STALE` 和 `ALERT_PAUSE`。
- **观察者以外的告警**：`runtime.py:396` `_alert(kind, key, message, severity="critical")`，写进同一本 `AlertBook`。
- **样本**：`SampleRecord`（`archive/models.py:342`）的 `data` 保存设备的完整负载，传感器值在 `data["sensor"]` 下。样本只插入一次，不改写。`received_at` 是主机时间。
- **安全配置**：`SafetyConfig`（`archive/models.py:196`）有 `version`、`rules`、`approved_by`、`approved_at`。批准走 `/wb/safety/approve`，存成只追加的记录。工作台的安全页用 JSON 编辑；起始模板在 `web/workbench/pages/safety-skeleton.js`，`tests/web/config-pages.test.mjs` 会核对模板字段和 `SafetyConfig` 一致。
- **规则用到的传感器**：保护规则 `SafetyConfig.rules[].sensor`；反馈规则 `RunSheet.feedback_rules[].sensor`（`archive/models.py:244`）。
- 项目规则：原始数据只追加；每次写入都有账本记录；文件不超过 800 行，函数少于 50 行；先写测试；测试只用模拟设备，不用网络和真机。

## 4. 意外开泵看门狗

### 4.1 在哪里运行

在执行 Agent 的 tick 里，紧跟第 1 步联锁之后，有没有阶段都运行（我的判断）。DiAGRI 模式下，水泵唯一合法的打开方式是操作员在人工接管期间调用灌溉路由，所以其他任何开泵都算意外，不管当时有没有实验在跑。

联锁已经设上时，第 1 步本来就在反复关泵，看门狗这一轮不动作。

**这个前提怎么保证。** 运行单的每个通道有归属：`host`（执行 Agent 写）或 `device`（AC5 定时器运行，GrowBridge 只读，`archive/models.py:67`）。现在的校验（`planning/validate.py`）只拦"写设备拥有的通道"和"开泵动作"，没有拦"把水泵设为设备拥有"。用户决定水泵永远不交给 AC5 定时器，所以校验新增一条阻断：运行单里水泵通道的归属是 `device` 时不通过（发现代码建议叫 `pump_device_owned`）。

已经批准过的旧运行单不重新校验；万一里面有设备拥有的水泵，看门狗照样会关泵，它本来就不看归属（我的判断）。`pump_off()` 会把插座模式写成 0，所以有人在 AC5 面板上给水泵插座设了定时，看门狗第一次动作时就会把它清掉；这正是这条规则想要的结果，告警文字要说明设备上的水泵模式已被重置。

### 4.2 什么时候算"意外"

三个条件同时成立（我的判断）：

1. 设备已连接，最近一份状态的读回显示水泵插座开着；
2. 控制服务没有正在进行的灌溉周期；
3. 这份状态是在我们最近一次灌溉结束**之后**收到的（用收到时的单调时间比较）。

第 3 条防止误判自己的灌溉：关泵命令发出后，状态还没刷新那几秒里，读回仍然是"开"。

### 4.3 动作

1. 调 `pump_off()` 关泵，触发名记为 `watchdog`，和联锁的 `interlock` 区分开。`pump_off()` 需要一个可选的触发名参数，默认仍是 `interlock`。
2. 发 critical 告警（种类 `pump_unexpected`，键 `pump`），经运行时已有的告警通道。关泵后收到的第一份显示水泵关着的状态会关闭这条告警，所以下一次意外开泵是新告警，会再通知一次（我的判断）。
3. 有阶段时，用 `Store.record_intervention`（`archive/store.py:420`）写一条干预记录，种类 `unexpected_watering`，带上这个阶段的实验和阶段编号；细节里记发现水泵开着的那份状态的时间、关泵确认的时间、关泵动作的请求编号。数据快照本来就收录时间窗里的干预记录（`archive/snapshot.py:75`），所以分析能看到这次意外浇水。不暂停阶段，也不新增阶段事件种类（我的判断：泵已经关了，要不要继续由操作员决定）。
4. 关泵没确认时，`pump_off()` 会设联锁，之后由第 1 步的联锁接手，看门狗不重复处理。

动作之后，要等收到一份在这次关泵**之后**的状态，才会再次判断，避免每个 tick 都重复关泵。如果新状态仍然显示开着，说明又被打开了，或者关泵没生效，再走一遍 4.3。

### 4.4 读不到状态时

已连接、也收到过状态，但状态里找不到水泵插座或者值无法解析：发 warning 告警（种类 `pump_unreadable`），不关泵，也不猜（我的判断）。还没收到第一份状态时不告警。状态重新读得出水泵插座时，这条告警关闭。

### 4.5 控制服务要新增的只读接口（名字是我的判断）

- `irrigating() -> bool`：是否有灌溉周期正在进行（现在只有私有的 `self._cycle`）。
- `pump_reading()`：返回水泵是否开着（`True`、`False`，读不出时 `None`）和这份状态收到时的单调时间。数据来源是 `control/device.py` `levels_from` 用的同一份 `data["outlet"]["O<n>"]["on"]`。
- 最近一次灌溉结束的单调时间。

## 5. 读数冻结检测

### 5.1 真机数据

本地仅桥接模式的数据库（2026-10-29 到 11-02，865 条样本，约 6 秒一条，最长连续 64 分钟，帐篷闲置，ppfd 为 0）里，各传感器的值保持完全不变的最长时间：

| 传感器 | 最长不变 | 说明 |
| --- | --- | --- |
| co2 | 不到 1 分钟 | 几乎每条都在变 |
| humi | 3 分钟 | |
| ppfd | 4 分钟（值为 0） | 夜里本来就是 0 |
| temp | 19 分钟 | 分辨率 0.1 °C |
| vpd | 18 分钟 | 由温湿度算出 |
| tempSoil | 42 分钟 | 土温变化慢 |

这份数据太短，也不是实验状态，只能说明各传感器的差别很大，不能证明门槛合适。门槛先用下面的默认值，以后用真实实验的数据再调。

### 5.2 判定规则

- **开始**：某传感器在最近 N 分钟里的每一条样本，值都**完全相同**（同一个数字），就开始一个冻结时段。
- **开始之前的计时**：值为空或不是有限数的样本直接跳过，不计入；两条相邻的有效样本之间的间隔超过 `max_gap_seconds`、或主机时间倒退，就算断开，从断开处重新计。
- **结束**：只有收到一个有效的、**不同的**值，冻结时段才结束。已经开始的时段里出现空档或无效值，不结束它，这些样本只是不计入；空档之后回来的还是同一个值，仍是同一个时段（我的判断：同一个卡住的探头不该因为链路时断时续被算成好几次、暂停好几次。链路本身的问题由已有的数据空档告警负责）。

AC5 报的值是取整过的（温度到 0.1 °C，CO2 到整数 ppm）。正常的传感器会在相邻值之间跳，卡住的会一直重复同一个数，所以用完全相等判断是可靠的。

### 5.3 门槛和配置

`SafetyConfig` 新增一个字段（字段名是我的判断）：

```json
"frozen": {
  "minutes": {"temp": 120, "humi": 60, "co2": 60, "tempSoil": 240},
  "max_gap_seconds": 600
}
```

- `minutes` 里没列的传感器不检查。默认不查 ppfd（夜里本来为 0）和 vpd（由温湿度算出，源头冻结已经会报）。
- 每个值必须是有限正数。
- 以前批准的、没有这个字段的安全配置照样能读出来，用默认值。还没有任何批准的安全配置时，也用默认值。冻结检测只会多出告警和暂停，不会放松任何限制，所以默认值不需要先批准才生效（我的判断）。
- 改门槛和改保护规则一样，要在工作台安全页提交并批准，留新版本。安全页显示当前生效的值；JSON 起始模板加上这个字段，前端测试的字段核对要跟着更新。

### 5.4 在哪里运行、多久查一次

在观察者里运行（我的判断：观察者是确定性程序，本来就负责告警和暂停）。从存储的样本判断，而不是观察者内存里的最新读数，这样重启不会把计时清零。最多每 5 分钟查一次（我的判断）：门槛最短 60 分钟，晚 5 分钟发现可以接受。

### 5.5 告警

- 每个冻结时段一条告警，种类 `frozen_reading`，键是传感器名；值一变就关闭。
- 有保护规则用到这个传感器时是 critical（这条保护规则已经失效），否则是 warning（我的判断）。

### 5.6 暂停

有阶段处于运行中（`RUNNING`），并且下面任一规则用到这个传感器，就暂停阶段：

- 当前安全配置里的保护规则；
- 当前阶段运行单里的反馈规则。

**"用到"包括派生量**（我的判断）：vpd 由温度和湿度算出，规则用到 vpd，就算用到 temp 和 humi。这张依赖表写在代码里。告警级别（5.5）也按同样的口径判断。

**每个冻结时段对每个阶段最多暂停一次**（我的判断）：

- 每次检查时，只要阶段在运行、用到的传感器处在未结束的冻结时段里、而这个阶段还没有因为这个时段暂停过，就暂停它。所以阶段在冻结期间开始、恢复或交还，也会在下一次检查时被暂停一次。
- 操作员看过后恢复阶段，同一个冻结时段不会再让它暂停；值变过以后又冻结，是新的时段，会再暂停。
- 暂停复用观察者已有的 `ALERT_PAUSE`。事件编号要由冻结时段和阶段一起组成，不能只用告警编号：工作流只暂停运行中的阶段，其他状态下收到的暂停事件会被记为丢弃，而用过的事件编号以后不能再用。

没有规则用到这个传感器时，只告警，不暂停（用户的决定）。

### 5.7 数据标记

不改原始样本的 `quality`，也不改任何样本。另写只追加的标记记录，放在样本所在的档案库里（表名和结构留给实现者）：

- 冻结时段**开始**：传感器、冻结的值、第一条冻结样本的时间、发现的时间；
- 冻结时段**结束**：传感器、最后一条冻结样本的时间、结束的时间、结束的原因。
  - 实现时的修订：原因是 `value_changed`（读数又变了）、`no_longer_listed`（安全配置里删掉了该传感器的阈值）或 `nothing_checked`（阈值表为空，什么都不查）之一，存在 `frozen_marks.reason` 列，由追加的迁移步骤加上，旧行为空。只有 `value_changed` 表示探头恢复；其余两种关闭的时段之后的数据不能当作可信，报告里这样的时段写“（不再检查）”。

开始和结束各写一条，不回头修改已有的行。数据快照列出和它的时间窗重叠的冻结时段，报告里也列出来，分析时就知道哪段数据可疑。

## 6. 闸门优先级

### 6.1 两级

| 级别 | 用途 | 位置 |
| --- | --- | --- |
| 紧急（0） | 保护写入 | `submit()`，写权是保护写权时 |
| 紧急（0） | 灌溉结束时的关泵 | `_run_cycle()` 的 `finally` |
| 紧急（0） | 交接 | `handover()` |
| 普通（1） | 定时、反馈、照料写入 | `submit()` |
| 普通（1） | 操作员手动写入 | `submit()` |
| 普通（1） | 灌溉开泵 | `_run_cycle()` |
| 普通（1） | 启动时核对未结记录 | `reconcile_unsettled()` |

`pump_off()` 不进闸门，保持不变。

### 6.2 锁的行为

- 级别小的先拿到锁；同级别先来先服务。
- 不抢占：正在执行的写入做完，才轮到下一个。所以紧急请求最多等一条写入。
- 等待中的调用被取消时，不能把锁弄丢：如果它在被取消的那一刻刚好拿到了锁，要把锁传给下一个等待者。被取消的等待者在交锁时跳过。
- 每个调用点显式传级别，没有默认值，审代码时一眼能看出各处用的是哪一级（我的判断）。
- 自己写，大约 40 行，不复制对方 MIT 许可的文件（我的判断）。放在 `control/` 下的一个新文件里。

### 6.3 不变的部分

进闸门后第一件事仍是 `_recheck`。排队期间写权被吊销的写入，进闸门后照样被拒。

## 7. 测试

所有测试用模拟设备和假时钟（`tests/control/conftest.py`、`tests/executor/executor_helpers.py`、`tests/observer/conftest.py` 里已有的工具）。

**看门狗**

- 面板把泵打开（模拟设备的外部改动），没有灌溉：下一轮关泵，账本里有一条触发名为 `watchdog` 的记录，发 critical 告警。
- 有阶段时写一条 `unexpected_watering` 干预记录，带实验和阶段编号；数据快照里能看到它；阶段状态不变。
- 关泵后第一份显示关着的状态关闭告警；之后再被打开，是一条新告警。
- 操作员灌溉期间不动作；灌溉刚结束、状态还没刷新时不动作。
- 关泵后还没收到新状态时不重复关泵；新状态仍是开着时再关一次。
- 关泵没确认：设联锁，之后由联锁接手。
- 状态里没有水泵插座：warning 告警，不关泵；读得出时告警关闭。
- 没有阶段时也运行。
- 运行单把水泵设为 `device` 归属：校验不通过，发现代码 `pump_device_owned`；把灯或风扇设为 `device` 归属仍然通过。

**冻结检测**

- 温度 120 分钟不变：一条告警，一条开始标记；值一变：告警关闭，一条结束标记。
- ppfd 和 vpd 不检查；`minutes` 里没列的传感器不检查。
- 时段开始之前，中间有超过 `max_gap_seconds` 的空档、时间倒退或无效值：重新计时，不报。
- 时段开始之后，出现空档再回来同一个值：仍是同一个时段，不新开告警，不再暂停。
- 重启观察者后，按存储的样本照样发现。
- 有保护规则或反馈规则用到：暂停一次；恢复后同一时段不再暂停；新的时段再暂停。没有规则用到：只告警。
- 阶段在冻结期间开始或恢复：下一次检查时暂停一次。
- 规则用到 vpd、而 temp 冻结：算用到，暂停；告警是 critical 还是 warning 也按这个口径。
- 保护规则用到时告警是 critical，否则是 warning。
- 没有 `frozen` 字段的旧安全配置照样能读，用默认值；非法值（负数、非有限数）被拒。
- 原始样本一条都没被改过。
- 快照列出重叠的冻结时段。

**闸门**

- 锁本身：级别小的先拿到；同级别先来先服务；被取消的等待者不泄漏锁；已拿到锁时被取消也会交出去。
- 一条保护写入越过排队的普通写入，只等正在执行的那一条。
- 灌溉结束时的关泵越过排队的写入。
- 交接越过排队的普通写入。
- 排队期间写权被吊销的写入，进闸门后仍被拒。

## 10. 最容易出问题的地方

1. 看门狗把自己的灌溉当成意外：4.2 的第 3 条必须有测试覆盖"灌溉刚结束、状态未刷新"。
2. `pump_off()` 会结束灌溉周期：看门狗必须先确认没在灌溉，再调用。
3. 优先级锁在取消时泄漏或重复释放：一旦出错，闸门永久卡死，所有写入都停。
4. 旧的安全配置因为新字段读不出来：`safety()` 读不出时，保护写权可能失效。要用真实格式的旧记录测试。
5. 冻结检测在树莓派上太慢。设备会主动推送状态，每份状态回包（包括写入后的回读）都存成一条样本，大约 6 秒一条，所以 240 分钟的窗口约有 2400 条。**不能**按条数设上限，否则门槛超过约 24 分钟时永远不会触发。可以在内存里按传感器增量记录（最后的值、这一段从何时开始），启动时从存储的样本重建一次；具体做法留给实现者，但要在树莓派上量一次耗时。
6. 真机上插座状态的读回可靠性没验证过。要在真机上确认后，才能说看门狗在真机上有效。
