# 模型调用记录与回放：设计

## 1. 意图

DiAGRI 的模型角色（编排、计划、研究、审计）在一次运行里会连续调用模型和工具。出了问题时，现在能看到的只有对话记录：回复文字最多 8000 字符，工具输入截到 1500、结果截到 2500（`dispatch.py:70`），思考内容和运行结束的原因都不在里面。开发工作台的 `--transcript`（`scripts/dev_workbench.py:225` 的 `RecordingClient`）记得多一些，但只在开发时能用，内容同样截断，没有思考内容和任务编号，也不能拿来重跑。

研究员要的是两样东西：

1. **一步步找出出问题的地方。** 一次运行从头到尾每一步模型看到什么、想了什么、调了什么工具、工具回了什么，完整可查。温室正式服务上出的问题也要能录下来。
2. **把问题变成可以重跑的东西。** 拿一份记录离线重跑，不调用模型、不花钱，看修过的代码在同一串模型回复下是否走对；跑通的记录可以变成回归测试。

这两样也是以后做基准测试（比较模型、effort、提示词）的基础：基准测试要的"这次运行成没成功、花了多少"会直接写在记录里。本设计不做基准测试本身。

**现状（`main`，54f101b）：**

- 所有模型调用都经过 `Dispatcher._run` → `run_agent`（`dispatch.py:252`、`loop.py:95`），没有别的调用点。
- `run_agent` 的 `observe(reply, outcomes)` 回调在一轮的全部工具执行完以后调用一次（`loop.py:134-139`）。
- 运行的结束原因在 `Dispatcher.run_task` 里决定，共五种：`denied`、`model_unavailable`、`model_stopped`、`undelivered`、`run_finished`（`dispatch.py:184-231`）。`_claim` 只运行状态为 `in_progress` 的任务（`dispatch.py:238`），并在运行前写入 `dispatch_claims`。
- 第一条用户消息里写着 `task_id`、`project_id` 和上下文里的轮次、协议、设备 id（`dispatch.py:129-131`）。工具会拿输入里的 id 和绑定的任务比对（`handlers_common.py` 的 `require_bound` 一类函数）。
- 预算在每次模型调用之前检查（`loop.py:114`），拒绝时抛出 `Denied`，拒绝码以 `budget_` 开头（`agents/budget.py`）。
- `RoleModel` 有 `model`、`effort`、`max_tokens`、`max_calls`、`tools`、`data` 和两项价格；非默认模型必须写价格（`config.py:17-45`）。
- 请求开了 `thinking: adaptive`（`llm.py:106`）。回复里的 `content`、`text`、`tool_calls` 是三个字段，循环用的是 `text` 和 `tool_calls`，`content` 原样回传；测试里有 `content=[]` 而 `text`、`tool_calls` 不空的回复。`content` 有 SDK 对象和字典两种形式（`sim/llm.py` 的 `ScriptedClient` 用字典）。
- `Tool` 只有 `reads_web`、`writes`、`sandbox` 三个标记（`tools.py:101`）。标了 `reads_web` 的只有 `lookup_crop_conditions` 和 `search_and_verify_sources`；计算作业工具（`submit_compute_job`、`get_compute_job`、`fetch_compute_artifacts`）会联网，但没有标记。
- 工具结果是字符串时原样传递（`tools.py:154`）；被拒绝时内容是 `Error: denied (<code>): …`（`tools.py:211`）。
- id 由 `new_id` 生成，形如 `<前缀>_<32 位十六进制>`（`archive/ids.py:12`）。时钟可以通过 `build_runtime(clock=…)` 注入（`runtime.py:615`）。正式服务用 `SystemClock`，开发工作台用带偏移的时钟，测试用 `FakeClock`。
- 报告文件按绝对路径存进档案（`research/report.py:86`），读取时 `archive.root.joinpath(artifact.path)` 仍指向原来的目录（`handlers_orchestrator.py:299-305`）。所以数据目录不能直接搬走用。
- 备份只复制六个 SQLite 数据库，不含 `archive/`、`agent_work/` 下的文件（wiki《Notifications, reports and backup》已写明）。
- 开发工作台不给 `--data-dir` 时，数据目录是退出就删除的临时目录（`scripts/dev_workbench.py:360-363`）；它每 30 秒自动跑一次待处理的任务。

## 2. 目标、非目标、反目标

**目标**

1. 配置开关 `model_trace`（默认关闭）。打开后，每次模型角色运行写一个记录文件，内容完整：角色配置、系统提示词、第一条消息、每次模型回复（包括思考内容）、每次工具调用的完整输入和结果、token、耗时、结束原因。
2. 开发工作台 `--trace`：除了记录，每次运行前把数据目录复制一份放在记录旁边，作为可靠回放的"运行前状态"。正式服务不做这一步。
3. `growbridge trace show FILE`：在终端里按步骤列出一份记录，不需要数据目录。
4. `growbridge trace replay FILE`：在运行前状态的临时副本上重跑这次运行。模型回复用录的，本地工具真实执行，会访问外部的工具用录的结果，每一步和记录比对，最后比对结束原因。
5. 测试里可以直接调用回放，一份记录加它的运行前副本就是一个回归测试。
6. 中英文档在同一个 PR 里更新。

**非目标**

- 基准测试的场景、评分和汇总（以后在这些记录之上做）。
- 工作台界面里查看记录。
- 自动删除旧记录或旧副本、限制总大小。
- 从某一步起改用真实模型继续跑（"分叉重跑"）。
- 正式服务上给每次运行拍快照。
- 把真实温室的记录提交进仓库（仓库是公开的）。

**反目标（即使能用也算失败）**

- 写记录或复制失败导致运行失败，或者开了记录以后 Agent 的行为有任何不同。记录层只读，不改请求和回复。
- 回放写入原来的数据目录或运行前副本，或者触达任何外部：设备、网页、计算作业、通知、心跳。
- 记录被当成研究证据：进入档案、备份或训练数据集导出。

## 3. 约束（来自现有代码）

- 运行的任务编号只能来自 dispatcher 的绑定，模型不能自己指定任务（`handlers_common.py:166` 的注释）。回放必须走同样的绑定。
- 工具结果里如果读过网页内容，`run_agent` 会隐藏写入和沙箱工具（`tools.py:175` 的 `restricted`）。回放必须保留这个行为，所以外部工具的录制结果要和原来一样经过 `Toolset`，不能绕开循环。
- 服务或工作台正在运行时 SQLite 也在写，复制数据库必须用在线备份接口（`archive/backup.py` 的 `copy_database`），不能直接复制文件。
- 记录和副本里有明文的用户消息、网页内容和工具结果。目录 0700，文件 0600。

## 4. 方案

考虑过三种做法，研究员选了方案一。

**方案一：每次运行单独记录，回放 Agent 的工作过程（选定）。** dispatcher 每启动一次运行，就给模型客户端和工具集各套一层记录器，一次运行写一个文件，结尾写下结束原因。回放时在数据目录的临时副本上绑定原来的任务，按原来的角色重跑一遍。代价是要改 `dispatch.py` 少量代码。

**方案二：沿用 `RecordingClient`，只补全字段。** 改动最小，但它只看得到每一次模型调用，不知道一次运行从哪开始、到哪结束，拿不到结束原因，只能靠"消息只有一条"来猜运行边界。基准测试最需要的正是结束原因，这个缺口会一直存在。

**方案三：完整重放整个 dispatcher，每次运行前给数据库拍快照。** 最忠实，但正式服务上每次运行都要复制整个数据目录，数据库越大越慢、越占空间。

研究员确认的另外三点：

- 记录在 `serve` 上也能打开，配置开关默认关闭。
- 运行前副本只在开发工作台 `--trace` 时自动做；正式服务不做，那边的记录主要用来一步步查看，回放只作参考。
- 文档修改放进这次的 PR。主检出目录 `docs/wiki-internals` 分支上未提交的 wiki 修改以后提交时再解决冲突。

## 5. 记录：何时、存在哪

- `Settings` 新增 `model_trace: bool = False`。
- 打开时，`make_dispatcher`（`runtime_agents.py:71`）把 `private_dir(data_dir / "model_traces")` 传给 `Dispatcher`。关闭时不建目录。
- 文件路径：`model_traces/<YYYY-MM-DD>/<task_id>-<HHMMSS>-<4 位随机>.jsonl`，日期和时间取运行开始时的本地时间。文件 0600。
- `Dispatcher.run_task` 在 `_claim` 成功之后、运行之前打开记录，结束时（五种结束原因的任何一种）写结尾并关闭。
- 模型调用由一个包在客户端外面的记录器写（拿得到耗时，模型抛出的错误也能记下）。工具调用由一个包在 `Toolset` 外面的记录器写（拿得到每个工具开始执行时的时钟时间和耗时）。两者都只读，原样转交请求和结果。
- 任何一行写失败：记 `log.exception`，这次运行不再写这个文件，运行本身照常（和 `_record` 的做法一致，`dispatch.py:296`）。
- 记录目录在 SQLite 之外，所以不进备份；训练数据集导出读的是档案、工作流和 agents 数据库，记录文件不在其中任何一个里。

## 6. 运行前副本（只在开发工作台）

- 开发工作台 `--trace` 打开 `model_trace`，同时让 dispatcher 在每次运行前复制数据目录。这个开关不是配置项，是 `Runtime` 上的字段 `pre_run_copies: bool = False`，只有开发工作台把它设成 `True`；`serve` 和配置文件都打不开它。
- 复制时机：`_claim` 写入 `dispatch_claims` 之后、第一次模型调用之前。这时的状态就是这次运行看到的状态。
- 位置：记录文件旁边的 `<记录文件名去掉 .jsonl>.pre/`，目录 0700。SQLite 用在线备份接口复制，其余文件普通复制，跳过 `model_traces/` 本身。
- 复制失败：记 `log.exception`，第一行里 `pre_run_copy` 为 `null`，运行照常。
- `--trace` 要求同时给 `--data-dir`：记录和副本要在工作台退出后还在。

## 7. 记录文件格式

一行一个 JSON 对象，`kind` 区分类型。所有时间 `at` 都是运行时时钟（`runtime.clock.now()`）的秒数；`seconds` 是单调时钟测的耗时。

**第一行，`kind: "run"`**

| 字段 | 内容 |
|---|---|
| `format` | `1` |
| `task_id`、`project_id`、`role` | 本次运行的任务 |
| `role_config` | 这个角色的 `RoleModel` 全部字段（`model_dump`）；没有配置这个角色时为 `null` |
| `system`、`system_sha256` | 系统提示词全文和它的 SHA-256 |
| `tools`、`tools_sha256` | 提供给模型的工具名列表；完整工具定义的 SHA-256 |
| `user` | 第一条用户消息全文 |
| `conversation_seq` | 运行开始时这个项目对话记录的最大序号；没有对话记录时为 `null`（回放时判断副本是否比录制新） |
| `clock_synced` | 运行开始时时钟的 `synced`；时钟没有这个属性时为 `null` |
| `data_dir` | 数据目录的绝对路径 |
| `pre_run_copy` | 运行前副本的目录名（相对记录文件）；没有时为 `null` |
| `growbridge_version` | `growbridge.__version__` |
| `git_commit` | 能取到就填（源码目录里 `git rev-parse HEAD`），取不到为 `null` |
| `at` | 运行开始时间 |

**每次模型调用，`kind: "model"`**：`turn`、`at`（调用前）、`seconds`、`stop_reason`、`text`、`tool_calls`（`id`、`name`、`input`）、`content`（全部内容块，转成字典，包括 `thinking` 和 `redacted_thinking`，签名原样保留）、`input_tokens`、`output_tokens`。模型调用抛出错误时改记 `error`（`类型名: 信息`），没有回复字段。

**每次工具调用，`kind: "tool"`**：`turn`、`at`（工具开始执行前）、`seconds`、`tool_use_id`、`name`、`input`、`content`（`ToolOutcome.content` 全文）、`is_error`、`external`。

**最后一行，`kind: "end"`**：`at`、`state`、`code`、`reason`、`params`（被拒绝时含 `denied_code`）、`denied`（被拒绝时是 `Denied` 的 `code`、`message`、`reason`、`params`，否则为 `null`；回放重现拒绝时用它）、`turns`、`input_tokens`、`output_tokens`、`cost`、`seconds`。运行在写结尾之前就崩溃时没有这一行，`trace show` 要显示"记录不完整"，回放以退出码 2 结束。

## 8. 外部工具标记

- `Tool` 新增 `external: bool = False`：调用它会访问本机以外的东西。
- 标为 `external` 的：`lookup_crop_conditions`、`search_and_verify_sources`、`submit_compute_job`、`get_compute_job`、`fetch_compute_artifacts`。
- 测试：每个 `reads_web` 的工具都必须是 `external`；全部 `external` 工具的名单和一份写在测试里的名单完全相同。新加一个联网工具时，测试会逼人做决定。

## 9. 查看：`growbridge trace show FILE`

- 先打印第一行的摘要（任务、角色、模型、版本、开始时间、有没有运行前副本），然后按 `turn` 逐步打印：思考内容、回复文字、每个工具调用的名称、输入和结果，最后打印结束原因和合计。
- 默认长内容截短显示，`--full` 显示全文。
- 打印前去掉控制字符和 ANSI 转义序列：记录里有网页内容，不能让它控制终端。
- 不读数据目录，不需要配置文件。

## 10. 回放：`growbridge trace replay FILE`

**状态从哪来。** 依次取：`--data-dir DIR`；记录旁边的运行前副本；配置里的 `data_dir`。来源是运行前副本时，结果可靠；另外两种只作参考，开头打印一行说明。恢复出来的备份不能作来源（不含 `archive/`、`agent_work/` 下的文件），文档写明。来源目录永远只读：先复制到一个临时目录（SQLite 用在线备份接口，其余文件普通复制，跳过 `model_traces/`），回放结束删除临时目录，`--keep-copy` 保留并打印路径。

**搬家。** 临时副本里，档案中按绝对路径存的文件路径（至少 `artifacts.path`），前缀从记录的 `data_dir` 换成临时目录。哪些列存了绝对路径，由实现者全部找出来，并用测试覆盖：运行前已经存在的报告在副本上能读。

**运行时怎么建。** 在临时副本上用 `build_runtime` 建运行时：

- 不调用 `runtime.start()`，transport 用模拟设备；
- 不配置计算服务、心跳和通知渠道（第二道保险：万一有外部工具漏标，它也没有可连的后端）；
- 时钟换成回放时钟：每次模型调用和每个工具执行之前，设成记录里这一步的 `at`；`synced` 返回记录的 `clock_synced`；
- 角色配置用记录里的 `role_config`（为 `null` 时这个角色不配置），不用当前配置；
- 预算换成回放预算：允许的模型调用次数和记录里的模型调用行数相同；记录的结尾是预算拒绝时，下一次检查按记录的拒绝码和信息重新拒绝；其余时候不拒绝、不扣费。

**怎么跑。** 和真实运行走同一条路：同样的 `bind_task`、同样的工具集构建、同样的 `_message`、同样的 `run_agent`，只是：

- 模型客户端换成回放客户端：按顺序交回录好的回复（用记录的 `text`、`tool_calls`、`content` 重建 `ModelReply`）；录的是错误就抛出错误；回复不够用时报告"回放需要的模型回复比录的多"并停止。
- `Toolset` 外面套一层：`external` 工具直接返回录好的 `ToolOutcome`，处理函数一次都不调用；其他工具真实执行，结果交给比对。
- 跳过 `_claim` 和 `_end`，任务状态不限。把 `run_task` 里决定结束原因的逻辑抽成一个纯函数，真实运行和回放都用它；回放用它算出"现在会怎么结束"，和记录里的 `code`（被拒绝时还有 `denied_code`）比对。在第一次模型调用之前就被拒绝的运行（没有配置角色、角色配置了不存在的工具）也这样比对：同样被拒绝就算一致。

**开始前的检查（只警告，不停）。** 副本里任务的状态不是 `in_progress`，或者这个项目的对话记录序号大于记录的 `conversation_seq` 时，警告"副本比录制新，结果可能不同"。系统提示词、工具定义的哈希或重新生成的第一条消息和记录不同时，各警告一次并说明哪一项不同。

**输出和退出码。** 逐步打印"一致"或"不一致"。遇到第一处不一致：打印工具名、输入、录的结果和回放的结果（两边都是 JSON 时按缩进格式化后给出差异），然后停止；`--keep-going` 继续往下比。最后打印两边的结束原因。退出码：`0` 全部一致（包括结束原因），`1` 有不一致，`2` 无法回放（文件格式不对、记录不完整、副本里找不到任务等）。

**测试里用。** 回放的核心是一个函数，输入一个运行时（由调用方按上面的规则建好）和一份记录，返回逐步的比对结果。命令行只是它的外壳。

## 11. 比对规则

一步工具调用算一致，要同时满足：`is_error` 相同；规范化以后 `content` 完全相同。规范化做四件事：

1. **id。** 匹配 `<小写前缀>_<32 位十六进制>` 的字符串换成 `<前缀>_*` 再比较。比较时如果两边同一位置分别是录的 id X 和回放的 id Y，就记下 X→Y；之后录好的工具输入在执行前把 X 换成 Y。映射在开始前先用一次：把记录的第一条消息和重新生成的第一条消息按同样的规则对齐，得到初始映射。在运行前副本上 id 本来就相同，映射为空；在测试用 fixture 建的状态上，映射让第一条消息里的任务、项目、轮次 id 对上。
2. **时间。** 回放时钟每一步设成录的 `at`。真实运行用的是会走的时钟，工具执行过程中读到的时间比 `at` 稍晚，所以两边都是 JSON 时，两个都大于 10⁹ 的数（按秒计的时间戳）相差不超过这个工具记录的 `seconds` 加 1 秒，算相同。
3. **路径。** 回放结果里的临时目录路径换成记录里的 `data_dir`。
4. **拒绝码。** 被拒绝的结果另外把 `denied (<code>)` 里的拒绝码单独列出，方便看（不影响是否一致）。

- **查看。** 打印的步骤顺序和内容；`--full`；控制字符被去掉；没有结尾时显示"记录不完整"。
- **回放客户端和回放预算。** 按顺序交回；录的错误照样抛出；回复不够时报告；预算拒绝在同一位置重现。
- **回放。** 在运行前副本上，同一份代码回放全部一致、退出码 0（用 `FakeClock` 和会走的时钟各测一次）；改动一个处理函数（monkeypatch）以后，在预期的那一步报告不一致、退出码 1；外部工具的处理函数被调用就让测试失败；id 映射（包括第一条消息的初始映射）让后面的调用对上；运行前已存在的报告在副本上能读；来源目录和运行前副本在回放前后的文件哈希完全相同；副本比录制新时有警告；没有配置角色、预算拒绝这两种运行的回放判为一致；格式不对或记录不完整时退出码 2。

## 17. 最容易出问题的地方

1. **状态和录制时不一样。** 正式服务上的记录没有运行前副本，用配置里的数据目录回放时，副本通常比录制新：任务已经结束，对话记录多了几条，第一个读状态的工具就会不一致。对策：开头说明"只作参考"、开始前警告、`--keep-going`、文档写清楚。
2. **会走的时钟。** 第 11 节的容差只覆盖按秒计的时间戳。按格式写出的时间、拿当前时间做的阈值判断（例如审计的 `due_at <= now`）在边界上仍可能造成假的不一致。实现时用"同一份代码、会走的时钟回放必须全部一致"的测试去找。
3. **其他会变的值。** 集合的遍历顺序、随机数等可能造成假的不一致，用同一个测试去找。
4. **外部工具漏标。** 一个漏标的工具在回放时会真的联网。对策是第 8 节的名单测试，加上回放运行时不配置计算、心跳和通知。
5. **绝对路径。** 漏掉一个存绝对路径的列，回放就会读到原来的目录（只读，但结果不对），或者被拒绝成"不在项目数据里"。对策是第 10 节的搬家测试。
6. **在线复制 SQLite。** 直接复制文件可能拿到写了一半的数据库，必须用在线备份接口。
7. **思考内容块。** `thinking` 带签名，`redacted_thinking` 是加密数据。必须原样保存，不能截断或改写。回放只把它们交回给循环，不发给 API，所以签名不需要验证。
8. **磁盘。** 完整的工具结果和每次运行的副本都占空间。默认关闭，不自动删除，文档里提醒排查完就关掉。
9. **外部工具的写入不会重放。** 外部工具（`submit_compute_job`、`fetch_compute_artifacts`）只返回记录下来的结果，它们对数据所做的写入在回放里不会发生，之后读取这些内容的本地步骤可能出现不一致，而代码并没有变。这是已知限制，文档里写明；回放的第一处不一致要结合这一点来读。

## 18. 设计时自行决定的事项

以下是设计时的判断，研究员没有逐项确认，请检查：

- 一次运行一个文件，按日期分目录；运行前副本放在记录旁边。
- 配置项叫 `model_trace`，只有开关，目录固定为 `data_dir/model_traces/`。
- 不自动删除旧记录和旧副本。
- 模型调用在客户端外壳里记，工具调用在工具集外壳里记（不用 `observe`，因为它拿不到每个工具的开始时间）。
- 新增 `Tool.external` 标记，而不是在回放里写死一个工具名单。
- 回放的状态来源顺序：`--data-dir`、运行前副本、配置里的 `data_dir`；恢复出来的备份不支持。
- 回放在临时副本里改写绝对路径，而不是把档案改成相对路径（那需要单独的迁移）。
- 回放用记录里的角色配置；预算按记录重现，不按副本里剩下的预算。
- 时间戳按"相差不超过工具耗时加 1 秒"比较。
- 第一条消息里的 id 先对齐一次，作为 id 映射的起点。
- 系统提示词、工具定义或第一条消息不同只警告，不停止。
- 遇到第一处不一致就停，`--keep-going` 继续。
- 在第一次模型调用之前就被拒绝、或因预算被拒绝的运行，回放同样被拒绝就算一致。
- 开发工作台 `--trace` 必须配 `--data-dir`；去掉 `--transcript` 和 `RecordingClient`。
- 不提交真实温室的记录进仓库；这次的测试在测试运行时自己生成记录和副本。
