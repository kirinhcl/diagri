# 多用户与温室锁定：设计

**日期：** 2026-11-16 · **状态：** 已批准（2026-11-16）；按第 1 轮审查修订（第 14 节） · **分支：** `feat/multi-user-locks`

## 1. 意图

DiAGRI 目前默认一个帐篷、一群平级操作员：任何操作员都能看到并操作任何项目和阶段。现场将有 12 个温室，由多位研究者并行使用。需要：

- 用户登录后勾选要用的几个温室，这几个就**锁定**给他；别人不能再选，已锁定的温室在列表里显示为不可选。
- 一个用户可以同时锁定多个温室，以便做温室之间的比较。
- 多个用户并行工作，互不干扰；每个用户**只能看到自己的东西**，管理员看全部。

分工（与 kirinhcl 商定）：本分支只做**用户与锁定这一层**。"一轮研究同时用多个温室做比较"（轮次、运行单、处理分配、报告分析从一台设备变为一组设备）以及"一个进程接入多台 AC5"都由 kirinhcl 负责。本层按温室编号工作，不关心设备如何接入。

## 2. 目标、非目标、反目标

**目标**

- G1 温室登记：系统知道有哪些温室（编号、名称、对应的 `device_id`）。
- G2 锁定：用户一次勾选若干温室，整组原子锁定；被锁的温室别人不可选；用户主动释放，管理员可强制释放；锁不随登录会话失效。
- G3 角色：普通用户与管理员。管理员管理用户和锁。
- G4 项目归属：项目归创建者；项目级写操作只有所有者（或第 6 节列明的管理员例外）能做。
- G5 操作权限：动阶段要同时满足"是项目所有者"和"锁着该阶段的温室"。
- G6 可见性：每个读取路由只返回调用者可见的内容；管理员看全部。
- G7 给 kirinhcl 的适配约定写清楚（第 11 节），PR 说明里重复一遍。

**非目标**

- 不做多设备接入（一个进程仍只控制 `settings.device` 这一台）。
- 不改轮次、运行单、处理分配、分析与报告的数据模型。
- 不收窄模型角色令牌的读取范围（现有已知限制，见 Wiki「状态与已知限制」）。
- 不做按用户路由的推送（Telegram/邮件仍发给配置的接收方）。
- 不做自助注册、通行密钥、用户组或项目共享。
- 不改旧的桥接入口（`api.py` 的 `/`、`/status`、`/history*`、`/activity` 与 `mcp_server.py`）。它们靠共享的 `settings.token` 访问；本设计把持有这个令牌的人视为管理员级别（部署者），在 Wiki 里写明。多用户层只在 `auto_research = true` 时生效。（实现者判断。）

**反目标**（做成这样就算失败）

- 任何未登记归属的东西默认对普通用户可见（必须默认只给管理员）。
- 用户能通过换一个路由、直接拼 id 或模型令牌之外的入口，读到或操作别人的项目、阶段、温室。
- 锁检查只在网页层做，`WorkflowService` 或控制入口可被绕过。
- 管理员能替别人审批或启动阶段。
- 两人同时锁同一温室时出现一人锁一半的状态。

## 3. 约束

**部署前提（用户确认）：** 只有一台树莓派，由它控制全部 12 个温室，即整个系统只有一份 DiAGRI 实例。锁、账号、项目都放在这一份实例里，不需要中央锁服务。

**来自现有代码：**

- 操作员只有名字和口令（`workbench/auth.py` 的 `operators` 表），无角色；只能用 `growbridge operator add` 添加。
- `Actor`（`ports.py`）只有 `kind/id/entry/reauth_at`。
- 项目表 `wf_projects(id, name, created_at)` 无所有者；轮次、阶段经 `project_id` 归属项目；阶段带 `device_id`。
- 各服务用独立 SQLite 文件（`runtime.py` 的 `DATABASES`）。没有单独的工作台库：`Operators` 已经放在 `dbs["workflow"]`，与 `wf_projects`、`wf_stages` 同库。
- 一个进程一台设备：`Settings.device` 单值，`control/service.py` 拒绝非本机 `device_id`。
- 告警（`observer/alerts.py` 的 `Alert`）只有 `kind` 与 `key`，不记录项目或温室。
- 他的分支更新频繁，改动尽量集中在新文件，对现有文件只做小而清楚的接入。

## 4. 方案

考虑过三种：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 门户在上层 | 每个温室一份完整 DiAGRI，上面加中央门户管账号与锁并转发 | 不动核心，但 12 份独立实例与以后的"一轮多温室比较"方向相反 |
| B 中央 DiAGRI + 远程控制服务 | 工作流集中，树莓派只跑控制服务 | 最适合跨温室比较，但要改"一进程一设备"的核心，越出分工 |
| **C 锁定层只认温室编号（选定）** | 在工作台/工作流里加温室登记、角色、锁、项目归属与可见性；设备怎么接入不管 | 落在分工边界内；多设备接入完成后本层不用改。代价：在多设备接入完成前，只有本机那台温室能真正运行阶段 |

用户选 C。

## 5. 数据

### 5.1 温室登记（配置）

`Settings` 新增 `greenhouses: list[Greenhouse]`，每项 `id`（如 `gh-01`）、`name`、`device_id`、`idle`（释放时写入的空闲状态，见第 6 节；默认灯 0、排风 30、循环扇 3、水泵关）。校验：`id` 与 `device_id` 各自唯一；`settings.device` 必须出现在列表中（为空时视为只有一个温室 `{id: "gh-01", name: "温室 1", device_id: settings.device}`，保持现有部署可用）。

### 5.2 角色

`operators` 表加列 `role TEXT NOT NULL DEFAULT 'user'`（`user` / `admin`）与 `disabled_at REAL`。`Actor` 加字段 `role: Literal["user", "admin"] | None = None`，由服务端从会话填入，请求体里的同名字段照旧忽略。停用用户时删除其全部会话；其持有的锁保留，由管理员决定释放。

### 5.3 锁

工作流库（与 `operators`、`wf_projects`、`wf_stages` 同库）新增：

- `greenhouse_locks(greenhouse_id PRIMARY KEY, holder, locked_at)`
- `greenhouse_lock_events(id, greenhouse_id, holder, action, actor, at, note)`，`action` ∈ `lock` / `release` / `force_release`。

锁定一组温室在一个事务里完成：任一温室已被锁（包括被自己锁）则整组失败，返回被占用的温室列表。锁与阶段同库，所以释放检查与阶段状态变更可以在同一事务里完成，不存在"刚释放就启动"的竞态。（实现者判断：放工作流库，不新建库，也不用改备份。）

### 5.4 项目所有者

`wf_projects` 加列 `owner TEXT`。`create_project` 记录创建者；模型或 `workflow` 身份创建的项目（若有）记为 `NULL`。迁移时已有项目 `owner` 为 `NULL`：只有管理员能看到，任何人都不能操作，直到管理员把它**转给**某个用户（见第 8 节转移路由）。所有者被停用时同理：管理员可转移项目，新所有者还须锁着相应温室才能动阶段。（实现者判断：用转移而不是让管理员代为操作，保持"管理员不替别人审批或启动"。）

## 6. 权限规则

记号：**所有者** = 项目 `owner` 等于调用者；**锁定人** = 调用者锁着该阶段 `device_id` 对应的温室。

| 操作 | 普通用户 | 管理员 |
| --- | --- | --- |
| 建项目 | 可以，成为所有者 | 可以，成为所有者 |
| 保存协议、建轮次、设预算、提研究目标、轮次选择与中止、冻结分析、登记留出、计算任务预算、录测量 | 所有者 | 所有者（管理员不能替别人操作） |
| 提交运行单（含模型起草） | 所有者，且所有者锁着运行单的 `device_id` | 同左 |
| 审批、启动、续跑、接管、交还、现场核对、手动写设备、灌溉、人工任务记录与计划灌溉 | 所有者且锁定人 | 所有者且锁定人 |
| 暂停、停止阶段 | 所有者且锁定人 | 任何阶段（紧急用），记录在阶段历史 |
| 安全配置审批 | 本机温室的锁定人 | 可以 |
| 告警标为已读 | 能看到这条告警的人 | 可以 |
| 证据卡录入、核实 | 可以 | 可以 |
| CSC 余额录入、计算尝试结算 | 不可以 | 可以 |
| 锁定、释放自己的温室 | 可以 | 可以 |
| 强制释放、管理用户 | 不可以 | 可以 |

释放规则：该温室上只要还有不处于 `ended` / `stopped` 的阶段（包括待审阅、已批准未启动），就拒绝释放，强制释放也拒绝；须先停止阶段或中止轮次。轮次处于两个阶段之间、下一个阶段尚未建立时允许释放。（实现者判断：比 `device_busy` 更严，避免别人锁走温室后本人的已批准阶段卡住。）

释放时的养护交接（用户确认）：`ended` / `stopped` 的阶段仍可能持有养护写入权并继续按日程写设备。释放（含强制释放）按顺序：①把本机控制的通道写到该温室配置的**空闲状态**并等回读确认；②交还养护写入权，并标记该阶段"养护已随释放结束"，重启后的 `restore_care` 不再为它重新签发；③删除锁。空闲写入未全部确认时释放失败（拒绝码 `idle_unconfirmed`），养护写入权恢复原状，锁保留。空闲状态写在温室登记里，默认灯 0、排风 30、循环扇 3 档、水泵关（通道只有 light / exhaust / fan / pump，只写本机控制的通道）；部署时按植物情况修改。

身份类型：所有者检查只针对 `operator` 身份。`model` 与 `workflow` 身份保持现有写入范围（模型角色按任务绑定的项目工作，见 `agents/handlers_common.py` 的 `bind_task`），但提交运行单时同样要求项目所有者锁着运行单的设备，否则起草就能把别人的温室钉死。多用户开启时，`POST /wb/drafts/run-sheet` 拒绝模型令牌（它没有任务绑定，模型只能经内部工具起草）。（实现者判断。）

检查放在哪里：项目与阶段的写操作在 `WorkflowService` 内检查（注入一个只读的 `Locks` 端口，查询某 `device_id` 的锁定人），工作台路由只负责把身份传进去；控制服务的手动写入与灌溉在工作台 `manual_stage` 处检查（控制服务本身不认用户）。

## 7. 可见性规则

| 内容 | 谁能看 |
| --- | --- |
| 项目、轮次、阶段（状态、运行单、历史、读数、测量、人工任务）、报告、对话、研究任务、预算、留出、分析状态、计算任务 | 项目所有者、管理员 |
| 温室实时环境（`/environment`）、安全配置（`/safety`） | 本机温室的锁定人、管理员。环境里的读数只给锁定时刻之后的；当前阶段、告警计数只给调用者可见的（用户确认：接手者看不到前一个使用者的历史读数） |
| 告警 | 按第 7.1 节归属 |
| 证据卡 | 所有登录用户（文献与手册引用，属公共知识） |
| CSC 总览（`/compute`） | 管理员；普通用户只看到自己项目的任务与尝试 |
| 收件箱 | 以上规则过滤后的结果 |
| `receipts/{request_id}` | 该动作所属阶段的所有者、管理员 |

看不到的东西按**该路由自己的"不存在"回答**（各路由现状不一：阶段 `state`/409、回执 404、留出与计算 `scope`/403），完整响应体（不只状态码）与查询一个随机不存在的 id 相同，并且不带出任何父对象的 id。`not_owner` 只在调用者能看到对象却不能操作时出现（即管理员对别人的对象）；`not_lock_holder` 只在所有者没锁温室时出现。

### 7.1 告警归属

告警表加两列 `scope_kind`（`project` / `stage` / `device`）与 `scope_id`，由产生告警的代码在 `raise_alert` 时显式给出；不按 `key` 前缀猜（阶段 id 可以含冒号，前缀匹配会把 `grow:1` 的告警配给 `grow`）。

- `stage` → 该阶段项目的所有者；`project` → 项目所有者；`device` → 该设备当前锁定人；
- 没有归属（系统类：备份、通知、心跳、运行健康等，或升级前已存在的告警）→ 只给管理员。

现有产生点逐个登记归属：`stage_waiting`、`task_missed`、`measurement_missing`、`measurement_outside_window`、`audit_finding`、`audit_task`（阶段）；`agent_task`、`task_deadline`（任务所属项目）；`frozen_reading`、`data_gap`、`threshold`、`pump_unreadable`、`pump_unexpected`、`pump_watchdog`（设备）。管理员看全部。

## 8. 接口

新增路由（都在 `/wb` 下，需登录）：

- `GET /greenhouses`：全部温室及状态（`free` / `mine` / `taken`）；普通用户看不到别人的名字，只看到"已被占用"，管理员看到锁定人。
- `POST /greenhouses/lock`：`{greenhouse_ids: [...]}`，整组原子锁定；需近期重新认证。
- `POST /greenhouses/{id}/release`：释放自己的锁。
- `POST /admin/greenhouses/{id}/release`：管理员强制释放，必填 `note`；需近期重新认证。
- `GET /admin/operators`、`POST /admin/operators`（添加，可设角色）、`POST /admin/operators/disable`、`POST /admin/operators/secret`（重置口令）：管理员；用户名放在请求体里（现有用户名可以含 `/`，放路径里会被路由拆开）；写操作需近期重新认证。
- `POST /admin/projects/{project_id}/owner`：管理员转移项目所有者，必填 `note`；该项目未结束阶段所在温室的锁**一并转给新所有者**（同一事务），否则新所有者拿不到锁、阶段无法继续；需近期重新认证。
- `GET /me` 增加 `multi_user`、`role` 与 `greenhouses`（自己锁着的）。控制台只在 `multi_user` 为真时显示温室与管理页。

命令行：`growbridge operator add` 加 `--admin`。第一个管理员只能用命令行创建。

## 9. 控制台

- 新页「温室」：12 个温室排成格子，空闲可勾选，自己的标"我的"，别人的灰显不可选；勾选后点「锁定」（弹重新认证）。自己的温室可「释放」。
- 新页「管理」（只对管理员显示）：用户列表（添加、停用、重置口令），锁列表（强制释放，填原因）。
- 其余页面不改布局，只因后端过滤而显示更少内容。新增文案中英双语，放进现有 i18n 目录。
- 登录后若用户没有任何锁、也没有项目，首页引导到「温室」页。

## 10. 测试

- 锁：并发锁同一温室只有一人成功；整组中一个被占则全组失败、无残留；有活动阶段时拒绝释放与强制释放；会话过期后锁仍在；停用用户后锁仍在。
- 权限：第 6 节表格每一行至少一个允许、一个拒绝用例；管理员不能审批或启动别人的阶段，但能暂停、停止。
- 可见性：用两个用户 A、B 各建项目、各锁温室，逐个读取路由断言 B 读不到 A 的任何东西（含收件箱、告警、回执）；未登记的告警 `kind` 对普通用户不可见。再加一个"路由清单"测试：枚举 `/wb` 下全部 GET 路由，要求每个路由都在可见性规则表里登记过，新路由未登记即失败（防止以后新增路由漏过滤）。
- 迁移：旧库升级后已有项目 `owner` 为空、只有管理员可见；未配置 `greenhouses` 时退化为单温室且现有测试不受影响。
- 控制台：Node 单元测试覆盖温室页的三种状态与锁定失败提示、管理页仅管理员可见。

## 11. 给 kirinhcl 的适配约定

1. **新的读取路由**要调用可见性检查，并登记进路由清单测试，否则测试失败。
2. **新的告警**在 `raise_alert` 时给出 `scope`（阶段、项目或设备）；不给时只有管理员能看到。
3. **多设备接入时**：`Locks` 端口已按 `device_id` 工作；运行单的 `device_id` 必须属于项目所有者锁着的温室——审批与启动已检查，计划角色起草时最好也只提供这些温室（可在 `project_context` 里加入所有者的温室列表）。
4. **一轮多温室时**：权限检查以阶段的 `device_id` 为单位，一组阶段要求所有者锁着组内每一个温室。
5. **新增"动阶段"的入口**，按第 6 节在 `WorkflowService` 内检查所有者与锁定人。
6. 锁表假定只有一个工作台实例持有；若改为多实例部署，锁表需集中。
7. 一台树莓派经蓝牙连 12 台 AC5 时，需要核实同时连接数上限（板载控制器常见约 7 个，未实测）与覆盖距离；可能要外接 USB 蓝牙适配器或轮流连接。这不影响本层。

## 12. 留给实现者

- 归属表、可见性检查的模块划分与函数名。
- 迁移脚本的具体写法（沿用 `db.migrate` 的追加步骤）。
- 控制台页面的组件拆分与样式细节（沿用现有 `ui/` 组件与 `tokens.css`）。
- 停用用户时其未结束阶段如何提示管理员（至少在管理页标出）。

## 13. 最容易出问题的地方

- **漏过滤的读取路由**：靠路由清单测试兜底。
- **授权与提交之间的时间差**：阶段命令在 `await` 之前授权；项目转移可能在中间发生。锁、所有者、阶段同在工作流库，所以在 `_commit` 的事务里再核对一次所有者与锁定人，不符就回滚（不在事务里 `await`，见 `archive/db.py` 开头的约定）。
- **收件箱与告警**：轮次与任务在 SQL 里先按所有者过滤再 `LIMIT`，计数用同一条件；否则别人的条目会在截断时挤掉自己的。
- **合并冲突**：对现有文件的改动集中在路由依赖注入与 `WorkflowService` 的权限检查点，新逻辑放新文件。

**修正现有代码里的问题（多用户开关关闭时也生效，因为它们本身就是缺陷）**

- 替换待审阅阶段的运行单时，`project_id`、`experiment_id`、`device_id` 必须与阶段记录一致，否则拒绝（`state`）。原因：写入权按运行单的设备签发，锁检查按阶段记录的设备做，两者分叉就能越权（R1-1，已复现）。
- 测量更正的目标必须属于同一实验，否则拒绝（R1-2，已复现）。
- 编排工具 `get_project_state` 的 `active_stage` 只在活动阶段属于所绑定的项目时返回，否则为 `null`（R1-8，已复现）。
- 现场核对 `record_onsite_check` 在 `workflow/recovery.py` 里，同样加检查点；被拒的请求不得触发任何控制侧动作（R1-5）。

**新增的规则**

- 提交运行单要求所有者锁着该设备（R1-3）；释放要交接养护（R1-4，见第 6 节）；项目转移同时转锁（R1-6、R1-12）；`_commit` 内复核（R1-6）。
- 告警按显式 `scope` 归属（R1-7、R1-13）。
- 环境页只给锁定之后的读数与可见的阶段、告警（R1-10）。
- 隐藏对象的回答逐路由对齐（R1-11）。
- 收件箱在 SQL 层过滤（R1-14）；计算总览对普通用户只列自己项目的任务、尝试与用量，余额与全局用量不给。
