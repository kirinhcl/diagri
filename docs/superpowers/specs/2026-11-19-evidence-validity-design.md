# 证据卡的有效性：设计

**日期：** 2026-11-19 · **状态：** 已批准（2026-11-19） · **分支：** `claude/focused-merkle-d5a027`

## 1. 意图

架构文档 §11.6 把记忆分四层，第三层"证据与跨轮经验"要求"分开记录原始观测、模型摘要、探索发现与已复核结论，关联来源版本、反证、适用条件和替代关系"。记忆设计（2026-11-17）§2 把"证据卡扩展（反证、适用条件、替代关系）"留到了以后，本设计补上这一块。

现状：一张证据卡是写入后不再修改的 JSON（`archive/models.py` 的 `EvidenceCard`），来源和核实另存为追加记录（`evidence_sources`、`evidence_verifications`）。`check_evidence` 只给三种提示：没有依据、未核实、未校准。系统里无法表达以下四件事：

- 一张卡被另一张取代了；
- 一张卡被撤回了；
- 两张卡互相矛盾；
- 一张卡只在什么作物、什么条件下成立。

于是计划角色可能一直引用一个已经过时的手册数值，审阅页也不会提醒。

这些数据以后要用来训练作物基础模型。被取代、被撤回、有矛盾的知识必须和有效知识区分开，而且要能回答"某个时刻它是否有效"。

适用条件通过变量目录和本体关联：条件里的变量用目录的标准编号，本体术语通过目录的 `refs` 关联；作物用 NCBITaxon 编号，和协议的写法一致。

## 2. 目标、非目标、反目标

目标
- 新卡可以写明它说的是哪个变量，以及适用的作物、品种、生长期和条件范围。
- 记录卡片之间的三种关系：取代、矛盾、撤回。计划角色可以提议；操作员可以确认、驳回、直接记录，或撤销已确认的关系。
- 卡片状态在读取时由记录推算出来，可以回答任一时刻的状态。
- 运行单引用了被取代、已撤回或依赖失效的卡片：挡住提交、审批和换单。引用有矛盾的卡片，或变量、单位、作物对不上：只给提示。
- 操作员可以把已交付轮次的结论转成本项目的 `local` 卡。
- 已批准和正在运行的阶段不被打断，只在阶段页和日报里提示。

非目标
- 往目录里加具体的新变量（光周期、DLI 等）。这需要单独做目录 v3，由研究者逐条确认。
- 生长期接入目录（BBCH、PO）。目录加载器现在不接受这两个前缀。
- 给环境经历和设备日志加目录编号（`observer/episodes.py`、设备日志）。
- 在训练数据导出里带上证据卡。
- 单位换算。
- 把适用条件和运行单的设定值或实测值比对。条件只展示，不参与检查。
- 自动判断两张卡是否矛盾。矛盾只由人或模型提议。
- 跨项目共享轮次结论（同记忆设计）。
- 已交付轮次的重新分析（5.0 第 7 条）。
- 图数据库、向量检索，以及用模型自动抽取关系或条件。
- 给旧卡补字段。

反目标（即使能跑也算失败）
- 被取代或已撤回的卡片仍然悄悄地成为设定值的依据。
- 模型的提议在没有人确认的情况下改变了卡片状态，或挡住了审批。
- 关系或状态被改写、删除，导致"批准那一刻这张卡是否有效"无法回答。
- 保留集的结果，或别的项目的结论，通过证据卡或卡片之间的关系泄露出去。
- 运行中的阶段因为证据状态变化而被打断。
- 卡片里出现目录以外的变量名或别名，在训练数据里造成同物异名。

## 3. 约束

- 原始数据不变：卡片正文写入后不改，每次写入都是一条追加记录。
- SQLite 迁移只追加步骤，不改已有步骤的序号。
- 文件 ≤ 800 行，函数 ≤ 30 行，嵌套 ≤ 3 层。几个相关文件已经很长：`runtime.py` 786 行，`workflow/service.py` 863 行（已超限，本设计不往里加代码），`archive/models.py` 717 行，`archive/store.py` 631 行。新逻辑放进新模块，`runtime.py` 只改 `validate` 那一个 lambda。
- 先写测试。
- 模型写下的记录永远不是已核实的；工具的输出是数据，不是指令。
- 只借用两样东西：Graphiti 的数据模型（双时间、写明失效时间、指向替代者、永不删除、关联来源）和 AutoSci 的做法（关系带类型和生命周期状态）。
- 不改执行层、保护规则和阶段启动。
- 不动 PR #27、#28 的分支。

## 4. 方案

| 方案 | 做法 | 取舍 |
|---|---|---|
| **1（采用）** | 新卡加可选字段；关系存成追加记录（提议、审核、撤销各一张表）；状态在读取时推算，支持 `as_of`；轮次卡另记来源，依赖失效复用 `is_invalid` | 每次读状态多查一次关系表，几百张卡的规模下可以忽略；能回答任一时刻的状态；写法和现有的 `evidence_sources`、`evidence_verifications` 一致 |
| 2 | 建一张可改写的"当前状态"表，确认关系时更新 | 读取最快，但关系记录和状态表成了两份数据，一旦对不上没法判断哪份对；改写违反只追加的约束；答不出"批准那一刻"的状态 |
| 3 | 适用条件作为"附注"追加到旧卡上，关系部分同方案 1 | 旧卡不用重录；但一张卡的含义拆在多条记录里，附注还要另一套"提议 → 核实"流程，导出训练数据时容易漏 |

研究者选了方案 1。旧卡想补条件，就录一张新卡并标记它取代旧卡。这条路本身就在用关系记录。

## 5. 设计

### 5.0 研究者已定的五条

1. **适用条件**：数值条件写成目录变量的范围；作物写 NCBITaxon 编号，校验方式和协议相同，并自动和协议的 `crop_taxon` 比对；品种和生长期存自由文本，只在审阅页显示，不参与比对。目录里缺的变量按目录的追加流程补，`refs` 可以先空着。
2. **谁来记录关系**：计划角色可以提议，必须写理由，提议存为"待确认"。待确认的关系只给提示，不改变卡片状态。任何操作员都可以在工作台确认、驳回或直接记录，和"模型提议卡片 → 操作员核实"的流程一样。
3. **审批**：引用被取代或已撤回的卡片，审批被挡住，审阅页写明替代卡；解决办法是改引替代卡，或改用 `user:` 输入。引用有矛盾的卡片，只给提示并列出矛盾的卡片。已批准和运行中的阶段不被打断，只在阶段页和日报里提示。
4. **比对**：反馈规则引用的卡片要比对三样：规则的传感器经目录别名解析后的变量与卡片的变量、单位、卡片作物与协议作物。对不上只给提示，分量与 `no_evidence` 相同。没有 `variable` 的旧卡不做比对。定时动作和护理步骤不比对变量，由 `calibrated` 标记覆盖。
5. **轮次结论**：轮次交付后，操作员手动把结论转成本项目的 `local` 卡，转卡本身就算核实。卡片的文字从报告复制，关联报告和快照，并带上报告的 `label`。没有转的结论仍然只出现在记忆的 `history` 里。转出的卡片在报告或快照依赖失效时一起失效，像撤回一样挡住审批，重新核对后才能再被引用。这类卡片只在本项目内可见。

审阅之后研究者又定了两条：

6. **取代只在同一范围内**：只允许两张公共卡之间、或同一项目的两张卡之间互相取代。轮次结论和公共卡冲突时记为"矛盾"：在本项目内只给提示，计划角色改引轮次卡。这样取代链永远是一条线，不会分叉，也不会成环。
7. **依赖失效的轮次卡不恢复**："重新核对"就是再做一轮实验，交付后转成新卡；旧卡永远失效。已交付是终态，同一轮不会有第二份报告，本设计不改轮次状态机。

下文标"〔提议〕"的是我补的决定，括号里写了理由。研究者在回放时已看过，可以改。

### 5.1 卡片的新字段（`EvidenceCard`）

| 字段 | 类型 | 规则 |
|---|---|---|
| `variable` | 目录编号或空 | 卡片的数值说的是哪个变量。必须是标准编号：写别名会被拒绝，并提示"用标准编号 X"；写已弃用的编号会被拒绝，并提示改用 `replaced_by`；写未知编号会被拒绝。只接受 `sensor` 和 `manual` 两类〔提议：`factor` 类的档位（如调光百分比）在不同来源之间不可比〕 |
| `unit` | 已有字段 | 填了 `variable` 且有数值时必须填写；按目录的 `unit_aliases` 归一后必须等于目录单位，存归一后的单位（如 `C` 存为 `Cel`）。原文单位留在 `citation` 里，系统不做换算 |
| `conditions` | `ApplicabilityRange(variable, min, max)` 的元组，最多 8 条〔提议〕 | 变量的规则同上（标准编号、非弃用、非 `factor`），同一变量不重复；`min`、`max` 至少填一个；`min ≤ max`；不能超出目录给该变量定的范围；单位就是目录单位，不另写。类名不用 `Condition`，因为 `models.py:168` 已有一个同名类 |
| `crop_taxon` | `NCBITaxon:<数字>` 或空 | 沿用协议的校验（`vocab/curie.py` 的 `taxon_problems`） |
| `cultivar` | 文本，≤ 200 | 同协议 |
| `growth_stage` | 文本，≤ 100〔提议〕 | 自由文本，不比对 |
| `conditions_note` | 文本，≤ 500〔提议〕 | 写目录还没覆盖的条件：光谱、栽培方式、测量位置、光周期或 DLI（在目录 v3 加进来之前） |

- 允许只写数值、不填 `variable`，被反馈规则引用时给 `uncataloged_card` 提示。
- 卡片里只出现 NCBITaxon 这一种本体编号，和协议一样。其他本体术语都通过目录的 `refs` 关联。
- 序列化：新字段为空时不写进 JSON，做法与 `ResearchProtocol._without_empty_fields` 相同，保证旧卡的正文和摘要不变。
- 三个写入口共用同一个校验函数 `card_problems(card, catalog)`（新模块 `vocab/card_checks.py`）：工作台的 `CardIn`、模型的 `propose_evidence_card`，以及 5.4 的轮次转卡。
- 比对时变量顺着 `replaced_by` 链解析到当前编号。目录新增方法 `Catalog.current(id)`：沿链走到底，遇到环就返回空〔提议：返回空时视为对不上，只给提示〕。

### 5.2 关系记录（新模块 `archive/evidence_relations.py`）

迁移新增三张表，都只追加：

```
evidence_relations(
  id TEXT PRIMARY KEY, seq INTEGER NOT NULL,
  kind TEXT NOT NULL,          -- supersedes | contradicts | retracts
  subject_id TEXT NOT NULL,    -- 取代者 / 被撤回的卡 / 矛盾的一方
  object_id TEXT,              -- 被取代者 / 空 / 矛盾的另一方
  reason TEXT NOT NULL,        -- ≤ 500 字
  source TEXT NOT NULL,        -- operator:<id> | model:planner
  task_id TEXT,
  project_id TEXT,             -- 生效范围，见第 6 节
  proposed_in TEXT,            -- 模型提议时任务所属的项目；操作员记录时为空
  at TEXT NOT NULL)
evidence_relation_reviews(relation_id PRIMARY KEY, decision, reviewer, note, at)   -- confirmed | rejected
evidence_relation_withdrawals(relation_id PRIMARY KEY, actor, reason NOT NULL, at)
```

三种关系的含义：
- `supersedes`：`subject` 取代 `object`。
- `retracts`：`subject` 被撤回，`object` 为空。理由比如论文撤稿、数值读错。
- `contradicts`：两张卡互相矛盾。存储时把两张卡的编号排好序，所以 (a, b) 和 (b, a) 是同一条，重复的会被拒绝。

生命周期：

```
模型提议 → 待确认 ──确认──→ 已确认 ──撤销（操作员，写理由）──→ 已撤销
                 └─驳回──→ 已驳回
操作员直接记录 ─────────────→ 已确认（审核人就是记录人，同一步写入）
```

- 每条关系的第一条审核记录生效，之后的不覆盖它；撤销同理。驳回和撤销都是最终状态，要重新主张就记一条新关系。
- 待确认的关系不能撤销，只能驳回。模型不能审核，也不能撤销。
- 关系从**确认时刻**起生效，到**撤销时刻**止。这就是借自 Graphiti 的双时间：每条关系的记录时间和失效时间都留在库里，旧记录永不删改。

写入和确认时的检查（确认时重新检查一遍，因为提议之后状态可能已经变了）：
- 两张卡都存在，并且对当前操作员或任务可见（第 6 节）。
- 卡片不能和自己建立关系。
- `supersedes` 的两张卡必须在同一范围内（5.0 第 6 条）：都是公共卡，或都属于同一项目。跨范围的会被拒绝，并提示改记 `contradicts`。
- `supersedes`：`subject` 必须仍然有效；`object` 不能已被取代，否则拒绝，并提示去取代它当前的替代卡。同一范围内的取代关系，写入时都看得到，所以这两条合起来就能保证取代链不分叉、不成环，不需要另做环检测。
- `retracts`：`subject` 不能已被撤回。
- 同类型、同一对卡，已有待确认或已确认未撤销的关系时，拒绝重复记录。

### 5.3 状态在读取时推算

`Archive.evidence_status(card_ids, project_id, as_of=None) -> Mapping[str, CardStatus]`：

| 字段 | 含义 |
|---|---|
| `validity` | `active`、`superseded`、`retracted`、`dependency_invalid` 之一 |
| `superseded_by` | 直接取代它的卡 |
| `current_replacement` | 沿取代链走到底的那张卡，并带上那张卡自己的状态 |
| `contested_with` | 和它有已确认、未撤销的矛盾，且对方仍有效的卡 |
| `pending` | 牵涉它的待确认关系的编号 |

- 几种状态同时成立时，按 `retracted` > `dependency_invalid` > `superseded` > `active` 的顺序取第一个〔提议：前三种挡得一样，顺序只影响提示语〕。
- `dependency_invalid` 只有轮次卡才可能出现（5.4）。
- `as_of`：只计入确认时间不晚于 `as_of`、且到 `as_of` 时尚未撤销的关系；依赖失效按 `invalidations.at` 判断。不传就是现在。
- 取代链的终点如果已被撤回，旧卡仍是 `superseded`（不会自动"复活"），审阅页提示"替代卡也已撤回，请录新卡或改用用户输入"〔提议〕。要让旧卡恢复有效，就撤销那条取代关系。
- 状态从不写入数据库。

### 5.4 轮次结论转卡

新路由 `POST /wb/rounds/{round_id}/evidence`，供操作员使用，必须能看到该轮所属的项目。

- 只有满足以下条件才能转：
  - 轮次已交付；
  - `memory_rounds.load_report` 没有降级，即报告不是 unavailable、invalid 或 held_out。这一条保证保留集的结果不会通过卡片泄露。
  - 每份报告只能转一次〔提议：同一结论不重复成卡〕。
- 卡片内容由服务端从报告和协议里取，不从请求体里取：
  - `source_class = "local"`；
  - `claim` 取报告的 `conclusion`，超过 1000 字就截断并加"…"，全文在关联的报告里；
  - `citation` 由服务端按"轮次、报告"的格式生成；
  - `variable` 取协议的 `primary_endpoint`，按 `Catalog.current` 解析；
  - `crop_taxon`、`cultivar` 取自协议；
  - `calibrated = True`（本地实测）。
- 请求体只能填 `growth_stage`、`conditions`、`conditions_note`，以及可选的 `value` 和 `unit`。`value` 默认为空〔提议：报告的效应量是处理与对照之差，不是可以直接作为设定值的数值，不自动填〕。
- 新表 `evidence_origins(card_id PRIMARY KEY, project_id, round_id, report_artifact_id, snapshot_ids, label, at)`。转卡在同一个事务里写入卡片、来源、核实（核实人就是转卡的操作员）和这条来源记录。
- 依赖失效：报告的制品或 `snapshot_ids` 里任一快照 `is_invalid` 时，状态为 `dependency_invalid`，判断方式复用 `memory_rounds._invalid`。依赖失效的卡不能恢复（5.0 第 7 条）：数据改正后要再做一轮实验，交付后转成新卡。
- 被引用的卡片 `label` 不是 `confirmatory` 时，给 `exploratory_finding` 提示，提示语里写明是哪个标签〔提议：`descriptive` 也算〕。
- 撤回一张文献卡，不会让引用过它的轮次失效：那一轮实验真实发生过，数据依然有效，有问题的只是当初选设定值的依据。

### 5.5 审批与提示

**挡住**（新模块 `planning/evidence_validity.py` 的 `check_evidence_validity(sheet, statuses)`；这几条 `Finding` 用默认的 `blocking=True`）：

| 代码 | 条件 | 提示内容 |
|---|---|---|
| `superseded_source` | 引用的卡已被取代 | 写明 `current_replacement` 及其状态 |
| `retracted_source` | 引用的卡已撤回 | 撤回理由 |
| `dependency_invalid_source` | 引用的轮次卡依赖失效 | 失效的快照或报告 |

接入方式：`runtime.py` 里给 `WorkflowService` 的 `validate` lambda 再拼上这组检查，项目编号取 `sheet.project_id`，状态从 `archive.evidence_status` 读。`_findings` 现有的调用点决定了它在哪些地方生效：

- **提交**（`service.py:175`）：运行单不入库，检查结果返回给计划角色。计划角色当场就能看到替代卡，在送审之前改好。
- **审批**（`:281`）：按审批时刻的状态检查。
- **给运行中的阶段换运行单**（`:613`）：检查新运行单。
- **启动阶段**（`start_stage`）：不跑检查。所以批准之后才失效的卡片，不影响阶段启动和运行，这符合 5.0 第 3 条。

**提示**（同一模块的 `check_evidence_fit`，和 `check_evidence` 一起由计划角色的处理器和 `review_json` 调用；用 `_hint`，不挡任何操作）：

| 代码 | 条件 |
|---|---|
| `contested_source` | 引用的卡有矛盾；列出矛盾的卡 |
| `pending_relation` | 引用的卡牵涉待确认的关系 |
| `variable_mismatch` | 仅反馈规则：`catalog.resolve(rule.sensor)` 经 `current` 解析后，和卡片 `variable` 经 `current` 解析后不同 |
| `evidence_unit_mismatch` | 仅反馈规则：规则单位按 `unit_aliases` 归一后和卡片单位不同 |
| `crop_mismatch` | 卡片和协议都写了 `crop_taxon`，而且不同 |
| `uncataloged_card` | 仅反馈规则：引用的卡有数值，但没有 `variable` |
| `exploratory_finding` | 引用的轮次卡标签不是 `confirmatory` |

- `crop_mismatch` 对三种引用（定时动作、反馈规则、护理步骤）都检查〔提议：作物和规则的传感器无关，一份番茄手册用在生菜项目里，不管它被哪种步骤引用都值得提醒；研究者原先的决定只说到反馈规则〕。
- `user:` 开头的引用照旧免检。
- 引用别的项目的卡片，按"卡片不存在"处理，给 `no_evidence`。

**已在运行的阶段**：阶段页按当前状态显示同样的提示。日报加一行：列出运行中阶段引用的、现在已失效的卡（编号、状态、替代卡），最多 5 条，由代码生成（`observer/report.py`）。

### 5.6 模型能看到和能做的

- `query_evidence`（`handlers_researcher.query_cards`）：
  - 返回的字段增加 `status`、`superseded_by`、`current_replacement`、`contested_with`、`pending`、`variable`、`conditions`、`crop_taxon`、`cultivar`、`growth_stage`、`conditions_note`、`label`（仅轮次卡）。
  - 新增 `variable` 过滤条件，会解析别名和 `replaced_by`。
  - 文本搜索默认只返回有效的卡（有矛盾的也返回，带标记），另外报告隐藏了几张：`hidden_inactive: n`。
  - 按编号查询时，失效的卡只返回编号、来源类别、引文、状态和替代卡，不返回 `claim` 和数值，和记忆处理失效报告的方式一致。
- 范围：公共卡加本任务所属项目的卡；别的项目的卡片编号按"不存在"回答。
- `propose_evidence_card`：新字段用 5.1 的同一个校验；仍然不能提议 `local` 卡。
- 新工具 `propose_evidence_relation(task_id, kind, card_id, other_card_id?, reason)`：
  - 仅计划角色可用，标记为 `writes=True`，所以读过网页内容的计划角色会按现有机制失去这个工具；
  - 每个任务最多 10 条〔提议〕；
  - 只能针对可见的卡；
  - 重复的待确认提议会被拒绝；
  - 存为待确认，来源记为 `model:planner`。
- 提示词增加：
  - 被取代、已撤回、依赖失效的卡不能引用，改引 `current_replacement`；
  - 引用有矛盾的卡时，在起草说明里写明各来源的适用条件和选用理由（架构文档 §6.2）；
  - 提议关系要写清理由，不能凭推测。
- 记忆的 `history` 不改。

### 5.7 工作台

- 证据页的列表增加状态标记、替代卡链接、矛盾的卡、待确认关系和新字段；可以按状态、变量筛选，也可以选 `as_of` 时间点查看。
- 状态和所在项目有关，所以证据页默认显示全局视角：只列公共卡，状态只算全局关系。页面上可以选一个自己能看到的项目，切换后加入该项目的卡，状态按该项目推算〔提议〕。`GET /wb/evidence` 因此另加 `project_id` 参数。
- 录卡表单增加新字段：`variable` 下拉框只列标准编号且不含 `factor` 类；条件逐行填写变量和上下限。
- 关系操作：记录（类型、另一张卡、理由），审核待确认的关系（确认或驳回，可写说明），撤销已确认的关系（必须写理由）。
- 轮次页：已交付且报告可用的轮次显示"转为证据卡"按钮；不能转时写明原因。
- 路由：
  - `POST /wb/evidence/relations`
  - `POST /wb/evidence/relations/{id}/review`
  - `POST /wb/evidence/relations/{id}/withdraw`
  - `POST /wb/rounds/{round_id}/evidence`
  - `GET /wb/evidence` 增加 `project_id`、`as_of`、`status`、`variable` 四个查询参数
- 关系相关的路由放在新文件 `workbench/evidence_relations.py`。模型角色调用这些路由一律以 `model_role` 拒绝，与现有证据路由相同。

## 6. 多用户

- **公共卡**（没有来源记录的卡）：所有登录用户可见；任何操作员都可以录入、核实，以及记录、审核、撤销两张公共卡之间的关系。这和多用户设计的权限表一致。
- **项目卡**（有 `evidence_origins` 的卡）：只有能看到该项目的人可见，判断用 `Access.require_project`，与轮次页的规则相同。转卡，以及记录、审核、撤销涉及项目卡的关系，也按这条规则。
- **关系的范围**：只要有一端是项目卡，关系就带上该项目的 `project_id`，并且只在该项目内可见、只在该项目内生效。计算状态时，带别的项目编号的关系一律忽略。
  - 例：项目 P 的轮次卡和一张手册卡 H 有矛盾。在 P 里，H 显示为有矛盾；在别的项目里，H 没有任何标记。别的用户既看不到这条关系，也不会因为 H 的状态变化推出 P 的结果。
  - 这种跨范围的关系只能是 `contradicts`。取代只在同一范围内（5.0 第 6 条），所以公共卡的"被取代"状态在所有项目里都一样。
  - 两端分属不同项目的关系一律拒绝，管理员也不例外〔提议：保持范围规则简单〕。
- **模型提议的去向**〔提议：计划角色写的理由可能带出本项目的结果〕：
  - 模型提议的关系记下 `proposed_in`（任务所属的项目）。
  - 待确认期间，这条提议连同理由和任务编号，只有能看到该项目的人可见。
  - 两张公共卡之间的提议被确认后在全局生效。确认人必须写说明，别的项目的人看到的理由就是这段说明；模型写的理由仍然只在 `proposed_in` 项目内可见。
- **操作员手录的 `local` 卡**保持现状，所有人可见：它本来就用来记本地经验，比如"这台温度探头偏高 1 °C"。录卡表单加一行说明：轮次结论请从轮次页转卡，那条路会检查保留集，并限定在项目内〔提议：不改现有录卡行为，人有意录入的内容由人负责〕。
- 模型能看到的和任务所属项目一致。
- **多用户关闭时**〔提议：沿用记忆设计 §3 "研究记忆照样给（本项目）"的先例〕：
  - 操作员的权限检查关闭：任何操作员都能在工作台看到、操作所有项目的卡和关系。
  - 数据仍按项目区分：状态按项目推算，模型只看到公共卡和本项目的卡。在项目 P 里记的关系不会挡住项目 Q 的审批，计划角色也引用不到别的项目的轮次卡。
  - `project_id` 照常记录。

## 7. 测试

- 单元测试：
  - 卡片校验：别名被拒；弃用编号被拒并提示替代编号；`factor` 类被拒；单位按别名归一；`min > max` 被拒；超出目录范围被拒；`crop_taxon` 格式；新字段为空时旧卡的正文和摘要不变。
  - `Catalog.current`：链式替代；遇环返回空。
  - 关系：待确认不改状态；确认；驳回是最终状态；操作员记录即确认；撤销后恢复；已被取代的卡不能再被取代；取代链不会成环；跨范围的取代被拒，跨范围的矛盾只在该项目内生效；矛盾按排序存储且重复被拒；确认时重新检查；模型提议的理由只在 `proposed_in` 项目内可见。
  - 状态：几种状态同时成立时的优先顺序；沿链找到当前替代卡；链的终点已撤回；`as_of` 早于确认、晚于撤销；依赖失效按 `invalidations.at`；矛盾只在对方有效时成立。
  - 检查：每个挡住代码和提示代码；`user:` 免检；传感器别名（如 `temp`）解析到同一变量；`replaced_by` 链；旧卡不做比对但给 `uncataloged_card`；`crop_mismatch` 只在两边都写了作物时出现。
  - 轮次转卡：held_out、invalid、unavailable、未交付、重复转卡都被拒；字段取自报告和协议；快照被标记后卡片变为依赖失效；引用后被挡住。
  - 范围：别的项目的卡给 `no_evidence`；涉及项目卡的关系在别的项目里看不到、也不生效；跨项目的关系被拒。
- 工作流：
  - 提交引用了被取代卡的运行单被拒，检查结果里有替代卡。
  - 审批被挡住。
  - 批准之后卡片才被取代：阶段照常启动，运行中的阶段继续运行。
  - 换运行单时检查新运行单。
- 工具：
  - 默认搜索隐藏失效卡并报告数量；按编号查询时降级；`variable` 过滤接受别名。
  - 提议关系：配额、重复、看不到别的项目的卡；读过网页内容的计划角色没有这个工具。
- 接口：各路由的权限；`model_role` 被拒；按 `as_of` 列出。
- 剧本模型端到端：
  1. 反馈规则引用手册卡 H；
  2. 计划角色提议"论文卡 P 取代 H"，操作员确认；
  3. 下一次提交引用 H 被拒，提示里点名 P；
  4. 一个已在运行、引用 H 的阶段继续运行，日报里有那一行；
  5. 一轮交付后转成 `local` 卡，然后标记快照失效，引用这张卡的运行单被挡住。
- 控制台：node 测试覆盖状态标记、关系表单和转卡按钮。

## 9. 已知局限

- 旧卡没有新字段。要补条件，只能录一张新卡并标记它取代旧卡。
- 适用条件只展示，不和运行单的设定值或温室的实测值比对；品种和生长期也不比对。
- 不自动发现矛盾，全靠人或模型提议。
- `factor` 类变量不能出现在卡片里，光照档位类的依据只能写进 `conditions_note`。
- 取代链的终点被撤回时，旧卡不会自动恢复，要人去撤销那条取代关系，或者录一张新卡。
- `WorkflowService.revalidate` 现在只有测试在调用。以后如果接到生产代码上，它会因为卡片失效而作废"已批准但还没启动"阶段的批准，这和 5.0 第 3 条冲突，到时需要另议。
- 关系只能在同一项目内或公共卡之间建立，即使是能看到两个项目的管理员，也不能跨项目关联。
- 轮次结论不能在本项目内取代公共卡，只能记为矛盾，所以只给提示、不挡审批。
- 依赖失效的轮次卡不能恢复。即使数据已经改正，也要再做一轮实验，才有新的可引用结论。
- 训练数据导出暂不带证据卡。以后要带时，以 `as_of` 推算出的状态为准。
- 操作员手录的 `local` 卡对所有人可见，系统不检查它是否抄录了保留集结果或别的项目的结论，只靠表单上的说明提醒。
