# Status and known limitations

[简体中文](../zh-CN/Status-and-Known-Limitations.md)

This page is for anyone who has to decide how far to trust the system: users, operators and contributors. It lists what has been verified and how, and what has not been verified or is not implemented. Every row names the place where you can check it.

The page was last checked against the working tree on 2026-11-10.

## In three lines

- DiAGRI mode has only ever run on the simulated AC5 ([`sim/device.py`](../../../src/growbridge/sim/device.py)). In that mode nothing has written to a real device.
- GrowBridge on its own (bridge-only mode) has read and controlled one real AC5 from a Mac. That record is older than the rest of the DiAGRI code.
- Nothing has been verified on a Raspberry Pi, with real notification services, or with CSC.

## Not verified or not implemented

"Not verified" means the code exists but has never run under the real condition. "Deployment item" means the design needs it and the code leaves room for it, but nothing in the repository sets it up. "Not implemented" means the code is missing.

| Multi-user (`multi_user`) | verified in tests only | Accounts, greenhouse locks, owners and per-operator visibility are tested on the simulated AC5 and through the workbench routes, not with real users or devices. One process still drives one AC5: the other registered greenhouses can be locked but run no stage until multi-device support exists. Releasing a greenhouse leaves the device at its current settings. The shared-token bridge routes (`/status`, `/history*`, `/activity`), the CLI `status`/`dashboard` and the MCP read tools still show every device's data to whoever holds the token. Protocol, run-sheet, stage, experiment and measurement ids are global: guessing another operator's id tells that it exists (nothing more). Until the next stage starts, new samples are still filed under the released stage's experiment. Notifications go to the configured recipients, not per operator. | [`workflow/access.py`](../../../src/growbridge/workflow/access.py), [adaptation notes](../../multi-user-adaptation.md) |

| Jobs on CSC | wired into `serve`, not verified against CSC | When `compute_templates_dir`, `compute_member` and the seven `FIRECREST_*` variables are all set, `serve` builds the compute service over `FirecrestBackend`. It follows the CSC and pyfirecrest documentation and has only been tested against a fake client. The API reports no CPU use and no billing balance: each job is charged at its template's full `max_cpu_hours` (and `max_storage_gb`), and an operator enters the project balance and each task's budget through the workbench (`POST /wb/compute/balance`, `POST /wb/compute/tasks/{task_id}/budget`). The Slurm state names are not documented: a state the code does not recognise (for example `SUSPENDED`) is an error, never "completed". Nor is it documented whether the job lookup finds jobs that have already finished, so a finished job that FirecREST no longer lists cannot be fetched or cleaned up. The tick reconciles unanswered submits and polls live jobs every minute; where the outcome is unknown (no job found, a cancel whose result cannot be read) the attempt is charged its whole reservation, and an operator can settle an attempt nobody can recover (`POST /wb/compute/attempts/{attempt_id}/settle`; `GET /wb/compute` lists the stuck ones). The states `DEADLINE`, `PREEMPTED`, `BOOT_FAIL` and `REVOKED` end an attempt as failed, `REQUEUED` and `REQUEUE_HOLD` keep it queued, `SUSPENDED` and `STOPPED` keep it running; this mapping follows the general Slurm manual, not CSC documentation. Without the full configuration the compute tools answer `unavailable`. | [`compute/firecrest.py`](../../../src/growbridge/compute/firecrest.py), [`runtime_compute.py`](../../../src/growbridge/runtime_compute.py), [`workbench/compute.py`](../../../src/growbridge/workbench/compute.py) |

| Backup | SQLite databases only | A backup copies the six DiAGRI databases. There is no image capture yet, so there are no images to back up. Without `backup_dir` nothing is backed up, and a standing warning says so. | [`runtime_backup.py`](../../../src/growbridge/runtime_backup.py), [`archive/backup.py`](../../../src/growbridge/archive/backup.py) |
| Snapshot freezing on the event loop | known limitation | Freezing a data snapshot (`freeze_dataset`) and re-checking it before a local analysis read and hash its files while holding a database transaction, on the same event loop that runs the 1 Hz executor tick. ## How to check again

```sh
.venv/bin/python -m pip install -c constraints-tested.txt -e '.[dev]'
.venv/bin/pytest -q
.venv/bin/growbridge simulate
```

The first command installs the test tools. The second runs the whole suite on the simulated AC5; add `-rs` to list the skipped tests and the reason for each. The third runs one simulated stage, as described in the [tutorial](Tutorial-Simulated-Round.md).

Checks on real hardware are recorded in [VALIDATION.md](../../../VALIDATION.md). A row moves to the first table once its check is recorded there.
